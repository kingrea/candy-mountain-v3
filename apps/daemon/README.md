# @candy-mountain/daemon

## Configuration

| Variable | Default | Purpose |
|---|---|---|
| `CM_DAEMON_HOST` | `127.0.0.1` | Bind address |
| `CM_DAEMON_PORT` | `4310` | Port |
| `CM_DATA_DIR` | `$XDG_DATA_HOME/candy-mountain`, else `~/.local/share/candy-mountain` | Data directory (`~` is expanded, relative paths resolve against the working directory) |
| `CM_SECRETS_KEY` | unset | Secrets master key: exactly 32 bytes, base64-encoded. Generate with `openssl rand -base64 32`. See [Secrets](#secrets) |
| `CM_AUTH_STRATEGY` | `development` | `development`, `password` or `trusted-header`. See [Auth](#auth) |
| `CM_AUTH_TRUSTED_HEADER` | unset | Header carrying the username; required with `trusted-header` |
| `CM_ADMIN_PASSWORD` | unset | Sets or resets the admin password at boot (any strategy). See [Password strategy](#password-strategy) |
| `CM_AUTH_SESSION_TTL` | `30d` | Password-strategy session lifetime: `<n>s`, `<n>m`, `<n>h` or `<n>d`, at most `400d` |
| `CM_AUTH_LOGIN_MAX_FAILURES` | `10` | Password strategy: failed logins allowed per username and per client IP within the window before `429` |
| `CM_AUTH_LOGIN_WINDOW` | `1m` | Password strategy: the failed-login window, same duration format as the session TTL |
| `CM_AUTH_COOKIE_SECURE` | `false` | `true` adds `Secure` to the session cookie; set it when the web app is served over https |
| `CM_SESSION_IDLE_TIMEOUT` | `15m` | Agent sessions: a live agent process with no turn for this long is killed (the session stays and resumes on the next prompt). Duration format as above, at most `7d` |
| `CM_SESSION_MAX_LIVE` | `4` | Agent sessions: live agent processes allowed at once; further prompts queue in order |
| `CM_DECISION_TIMEOUT` | `5m` | Agent sessions: how long a permission request or question waits for an answer before the agent is refused. Duration format as above, at most `1d` |
| `CM_WORKTREES_PER_PROJECT` | `4` | Worktrees: active worktree leases allowed per project; an acquire beyond it is refused. See [Worktrees](#worktrees) |
| `CM_WORKTREE_IDLE_TIMEOUT` | `2h` | Worktrees: a lease unused this long is reclaimed if its worktree holds no uncommitted or unpushed work (`90s`, `15m`, `2h`, `1d`; at most `30d`). See [Worktrees](#worktrees) |
| `CM_WORKTREE_RECLAIM_INTERVAL` | `10m` | Worktrees: how often the idle reclaim pass runs |
| `CM_WEB_URL` | `http://127.0.0.1:4300` | Origin of the web app, used to build the absolute links in Slack notifications. See [Notifications](#notifications) |
| `CM_UPTIME_HISTORY_MAX` | `500` | Uptime: stored checks kept per monitor; older ones are pruned as new checks land. See [Uptime monitors](#uptime-monitors) |
| `CM_UPTIME_HISTORY_MAX_AGE` | `30d` | Uptime: stored checks older than this are pruned whatever the count (`12h`, `7d`; at most `366d`) |

`~/.candy-mountain` is not used because Candy Mountain v2 owns it. Keep the data directory outside any repository.

## Data directory

Created on start (mode `0700`) if missing:

```
<data dir>/
  candy-mountain.db   SQLite database (WAL mode, so -wal/-shm files appear while running)
  secrets/            encrypted secret values, see Secrets
  worktrees/
  agent-homes/
  logs/
  run/                pid files
```

Moving to another machine is a copy of this directory with the daemon stopped.

## Database

One SQLite database through Drizzle (`better-sqlite3`). Pending migrations run automatically on every daemon start; a start with nothing pending changes nothing.

- Schema: `src/db/schema/`, one file per table group, each re-exported from `src/db/schema/index.ts`.
- Migrations: `drizzle/`, generated by drizzle-kit and committed. Never edit an applied migration.

### Adding a table

1. Create `src/db/schema/<name>.ts` with `sqliteTable(...)` and add `export * from './<name>'` to `src/db/schema/index.ts`.
2. `pnpm --filter @candy-mountain/daemon db:generate --name <short_name>` writes `drizzle/NNNN_<short_name>.sql` plus a snapshot and journal entry.
3. Review the SQL, commit it with the schema change. The next daemon start applies it.

`src/db/schema.test.ts` fails when the schema has changes without a generated migration. `db:check` validates the migration folder; `db:studio` opens Drizzle Studio on the configured database.

Drizzle applies a migration only if its journal timestamp is newer than the last applied one, so when two branches both add migrations, regenerate the later one after merging rather than keeping both as-is.

### Using the database

`startPlatform(dataDir, { product })` (`src/platform.ts`) is platform start. `product` is required and is the only thing that says what runs: the platform keeps no default capability, module or plugin type list of its own and imports no product capability. It creates the directory tree, opens and migrates the database, walks the platform's own definitions (`platformDefinitions()` in `src/platform-capabilities.ts`, today the `threads` session store) followed by the product's definition list (validated and ordered by `createCapabilityRegistry` before anything touches disk, started dependencies first by `startCapabilities` in `src/capabilities/start.ts`), starts the agent MCP host over the definitions' MCP servers and the notification dispatcher over their channels, and returns `{ product, paths, db, secrets, capabilities, modules, pluginTypes, families, runtime, agentMcp, notifications, close }`; `close` closes the started definitions in reverse and the database last. Nothing on `Platform` is specific to a capability: a capability's services are read from the started list with `platform.runtime.service(KEY)`, the key exported by the definition that offers it. The product (`Product` in `src/product.ts`) joins the shared configuration (`CANDY_MOUNTAIN_PRODUCT` in `@candy-mountain/shared`: name, scope label and the capability, module and plugin type ids) with what the daemon runs: the entry point (`src/index.ts`) builds it with `candyMountainProduct(options)` in `src/candy-mountain.ts`, which takes `capabilityDefinitions(options)` (`src/definitions.ts`), `MODULES` and the plugin types no capability brings (`PLUGIN_TYPES`). Before anything else `assertProduct` refuses boot with `ProductError` naming every id the configuration lists that nothing supplies, or that is supplied but not listed; the capability list names service-only definitions (`slack`) too.

`createApp(deps)` (`src/app.ts`) is the app factory. `deps.product` is required too; `capabilities`, `modules`, `pluginTypes` and `families` are built from it when not passed (the entry point passes the platform's). It exposes `db`, `paths` and the registries to routes as `c.var` (type routes with `new Hono<AppEnv>()`), mounts the platform's own routes, each started definition's `workspaceRoutes` under `/projects` and `platformRoutes` at their paths, runs `onWorkspaceDeleted` hooks before a project row goes, and serves chat threads when the runtime offers `THREAD_SESSIONS` (with `THREAD_BOTS` and `chatFamilies` when offered). `AppDeps` has no field for any one capability. `GET /info` answers `{ version, dataDir, authStrategy, productName, scopeLabel }` from the product, so the web app need not import the constants. Services take `db: Db` as a parameter rather than importing a global.

`src/seam.test.ts` keeps it that way: it fails when `platform.ts` or `app.ts` imports, directly or through a folder barrel's re-exports, any product capability folder (`acp`, `assignees`, `bot-sessions`, `bots`, `chat-claude-code`, `chat-codex`, `decisions`, `deployments`, `environments`, `issues`, `posture`, `sessions`, `slack`, `team`, `uptime`, `worktrees`), any plugin type folder under `plugins/`, or the product's composition (`candy-mountain.ts`, `definitions.ts`). Session families (`src/threads/families.ts`) and the plugin type and module registries (`plugins/registry.ts`, `modules/registry.ts`) are platform and imported by path.

Tests use `openTestDatabase()` (in-memory, migrated) or `createTempDataDir()` from `src/testing`, and the helpers in `src/testing/platform.ts`: `startTestPlatform(dir, { capabilities?, modules?, pluginTypes?, product?, ...platformOptions })` boots Candy Mountain (or `product`) with those parts swapped and the configuration's ids following them; `withoutCapabilities(...ids)` gives Candy Mountain's definitions without those ids and its modules trimmed to match, for booting a chosen subset; `CAPABILITY_DEFINITIONS` is Candy Mountain's full list to filter or swap entries in; `createTestApp(deps)` is `createApp` with the product defaulting to Candy Mountain, for route tests that pass their own registries or runtime; `platformApp(platform, deps?)` is the app the entry point would build over a started platform.

## Secrets

`src/secrets/` stores tokens and keys for plugins, bots and auth. Each value is encrypted with AES-256-GCM under `CM_SECRETS_KEY` (random 12-byte IV per write; owner and name bound in as associated data, so a file copied to another slot fails to decrypt) and written atomically to `secrets/<owner>/<name>.json` with mode `0600` inside `0700` directories. Owners and names are 1-128 of letters, digits and `. _ : @ -`, starting with a letter or digit.

Keep the key outside the data directory and back it up separately: moving machines means copying the data directory and setting the same key. Without it the values cannot be recovered.

If `CM_SECRETS_KEY` is unset the daemon still starts, logs a warning, and the store is locked: `set` and `get` throw `SecretsLockedError`, while `isSet`, `delete` and `deleteOwner` keep working. A malformed key (not base64, or not 32 bytes) stops the daemon at boot.

`startPlatform(dataDir, { product, secretsKey })` returns the store as `platform.secrets`:

- `set(owner, name, value)`, `isSet(owner, name)`, `delete(owner, name)`, `deleteOwner(owner)` (returns the number removed). Delete an owner's secrets when deleting the owner.
- `get(owner, name)` returns the plaintext or `undefined`; it throws `SecretDecryptError` when the key is wrong. Only daemon-side services may call it.
- `platform.secrets.writeOnly` is a frozen view without `get`. It is the only form route handlers may receive; never put the full store in `c.var` or return a value over HTTP.

Errors name the owner and secret but never carry the value or the underlying crypto error. Tests use `createSecretsStore(dir, MasterKey.generate())` from `src/secrets`, with `dir` inside `createTempDataDir()`.

## Mastra

Mastra runs as a library only (no server routes or Studio). `createMastra(paths, { agents? })` in `src/mastra.ts` points a `@mastra/libsql` store at `candy-mountain.db`, creates its `mastra_*` tables, registers the agents the optional factory returns (it receives the store, so agent memory shares the file) and returns `{ mastra, storage, close }`; the platform-agent definition (`src/platform-agent/definition.ts`) creates it once at start with the platform agent, waits for it on the first turn, and shuts it down in its close after cancelling the turns still streaming. Those tables, including the memory ones, are Mastra's own: never add them to the Drizzle schema or migrations. Nothing here needs an API key or the network until a turn runs.

## Projects and organisations

`src/projects/` owns both. Routes are mounted at `/projects` and `/organisations` (the web proxy maps `/api/*` to them); wire types live in `@candy-mountain/shared` (`projects.ts`, `slug.ts`, `api-error.ts`). Other daemon code resolves a project with `getProjectBySlug(db, slug)` / `findProjectBySlug` and its checkout with `sourcePath(project.source)`.

A project's local path is checked on create and update (must be an absolute existing directory, `~` expanded) and the facts are stored as `verification` (`pathExists`, `hasBeads`, `isGitRepo`, `hasRemote`, `remoteName`, `remoteUrl`). `POST /projects/:slug/verify` re-runs the check; a vanished path is recorded, not an error. Errors are `{ error: { code, message } }`.

## Issues

`src/issues/` reads a project's issues through the `bd` CLI in its checkout (`sourcePath(project.source)`); the platform keeps no copy. Routes are mounted under `/projects/:slug/issues` (wire types in `@candy-mountain/shared` `issues.ts`):

- `GET /projects/:slug/issues` -> `{ issues: Issue[] }`: every issue including closed (`bd list --all --limit 0`), `ready` from `bd ready --limit 0`, outgoing `dependencies` edges.
- `GET /projects/:slug/issues/:id` -> `{ issue: IssueDetail }` with `dependsOn` and `dependents` (children are dependents of type `parent-child`).
- `GET /projects/:slug/issues/dependencies?ids=a,b` -> `{ dependencies: IssueDependency[] }`, outgoing edges of each id; unknown ids contribute nothing.
- `GET /projects/:slug/issues/:id/comments` -> `{ comments: IssueComment[] }`.

`runBd(cwd, args, { timeoutMs })` appends `--json`, refuses a checkout without `.beads` (bd would otherwise use an enclosing workspace), drops `BEADS_DIR`/`BEADS_DB` from the environment, times out after 15s, and treats an `{ error }` payload as a failure even when bd exits 0. Errors are `IssueError`: `no_issue_tracker` 422, `not_found` 404 (unknown id), `invalid_request` 400, `tracker_failed` 502 (bd's own message), `tracker_unavailable` 503 (no `bd` on PATH), `tracker_timeout` 504.

The list is cached per project for `ISSUE_LIST_TTL_MS` (3s) and concurrent reads share one bd run. Anything that changes a project's issues calls `invalidateIssueList(projectId)`. Tests inject a fake runner with `createIssuesService({ run })` and `issueRoutes(service)`; `createTempBeadsWorkspace()` in `src/issues/test-workspace.ts` makes a real throwaway workspace.

`GET /projects/:slug/issues/events` is a server-sent event stream (browser: `new EventSource('/api/projects/<slug>/issues/events')`, path helper `projectIssueEventsPath`). It sends `: connected` at once, `: ping` every 30s (the web proxy's fetch drops bodies silent for 300s), and `event: changed` with `data: {"projectId":"..."}` when the project's issues change on disk; clients refetch on `changed`. The stream ends when the daemon shuts down.

`startIssueWatcher({ db })` (`src/issues/watcher.ts`, started by the issues capability definition (`issuesDefinition` in `src/issues/definition.ts`, offered as `ISSUE_WATCHER`) and closed with the definitions) keeps one recursive `fs.watch` on `.beads` per active project, shared by every subscriber. Events are debounced (250ms quiet, at most 1s per burst), notifications are spaced at least 2s apart (a scripted run of bd writes is many processes, not one flurry), and changes are detected by fingerprint: the Dolt `manifest` and journal length plus `issues.jsonl`, because bd rewrites Dolt files on every read and raw events would make each refetch trigger another. A real change calls `invalidateIssueList` and notifies subscribers. Every 2s it re-reads the active project list (new, archived, deleted, moved) and re-checks each `.beads` directory, so the directory appearing, disappearing or being recreated is picked up.

Writes (`src/issues/writes.ts`, routes in `write-routes.ts`, request types in `issues.ts`) all go through bd with `--actor=<platform username>`, and every one calls `invalidateIssueList` even when it fails part way. Bodies are validated up front (400 `invalid_request`); bd's own refusals come back as 502 `tracker_failed` with its message.

- `POST /projects/:slug/issues` `CreateIssueRequest` -> 201 `{ issue: IssueDetail, warnings }`. `dependsOn` edges are added one `bd dep add` at a time after the create; any bd refuses (unknown id, an epic blocking a task) land in `warnings` while the issue stays created. A parent's labels are inherited (bd default).
- `PATCH /projects/:slug/issues/:id` `UpdateIssueRequest` -> `{ issue }`. Omitted fields are untouched; `null` or `''` clears text, `assignee` and `parentId` (detach); `labels` replaces the whole set.
- `POST /projects/:slug/issues/:id/close` `{ reason?, force? }` (body optional) -> `{ issue }`; `force` closes despite open children or open blockers, which bd otherwise refuses (502 with its message).
- `POST /projects/:slug/issues/bulk` `{ ids, changes }` -> `{ updatedIds, missingIds }`: one `bd update <ids...>` call (at most `MAX_BULK_ISSUE_IDS`); bd skips unknown ids, which come back in `missingIds`. `changes` takes `status`, `priority`, `type`, `assignee`, `parentId` (`null` detaches), `addLabels`, `removeLabels`.
- `POST /projects/:slug/issues/:id/comments` `{ text }` -> 201 `{ comment }`; the text goes through a temp file so a leading dash is not read as a flag.
- `PATCH /projects/:slug/issues/:id/comments/:commentId` `{ text }` -> `{ comment }` as bd reads it back.

bd 1.2.2 cannot edit comments and `bd sql` is refused in embedded mode, so `editCommentInDolt` (`comment-edit.ts`, the one place to swap out once bd can) asks `bd dolt show` for the embedded database, then pipes an `UPDATE comments ... WHERE id AND issue_id` plus `DOLT_ADD`/`DOLT_COMMIT` to `dolt --data-dir <dir> sql`, with all user text as hex literals. It needs `dolt` on the daemon's PATH (503 otherwise), only works in embedded mode, and retries while a bd process holds the store (the dolt CLI then opens it read-only). `.beads/issues.jsonl` picks the edit up at bd's next export, not immediately.

## Auth

Every request passes one middleware (`src/auth/middleware.ts`) that asks the configured strategy for an actor. Routes read `c.var.actor` (`{ id, username, displayName, roles }`, type `Actor` from `@candy-mountain/shared`) and never a header or cookie. No actor means `401 { error: { code: 'unauthenticated' } }`. Only `PUBLIC_PATHS` (`/health`, `/auth/strategy`) and a strategy's own `publicPaths` skip the check; `c.var.actor` is unset there.

Strategies, chosen with `CM_AUTH_STRATEGY` at boot (an invalid value stops the daemon):

- `development` (default): every request is the admin.
- `password`: a server-side session identified by a cookie, issued by logging in. See [Password strategy](#password-strategy).
- `trusted-header`: the value of `CM_AUTH_TRUSTED_HEADER` is matched exactly against `users.username`; missing, empty or unknown is a 401. Only safe when a proxy in front of the web app overwrites that header on every request and nothing else can reach the web app or daemon, since the web proxy forwards browser headers unchanged.

Users live in `users`, roles in `roles` (keyed by `slug`), membership in `user_roles`. `seedAuth` runs on every start and ensures the `admin` user holding the `admin` role exists. `GET /auth/me` returns `{ actor }`. `GET /auth/strategy` is public under every strategy and returns `{ strategy }`, so a login page can tell whether to show itself before anyone is signed in.

### Password strategy

- `POST /auth/login` with JSON `{ username, password }`: `200 { actor }` plus a `cm_session` cookie (`HttpOnly; SameSite=Lax; Path=/; Max-Age=<ttl>`, `Secure` with `CM_AUTH_COOKIE_SECURE=true`). A wrong username or password is `401 { error: { code: 'invalid_credentials' } }` and creates no session; a malformed body is `400 invalid_request`. Logging in replaces the session the request's cookie held.
- `POST /auth/logout`: deletes the session, clears the cookie, `204`. Public, so an expired cookie can still be cleared.
- Login is rate limited in memory (reset on restart): more than `CM_AUTH_LOGIN_MAX_FAILURES` failures within `CM_AUTH_LOGIN_WINDOW` for a username or for a client IP gets `429 { error: { code: 'rate_limited' } }` with `Retry-After` before the password is checked. A successful login clears that username's counter. The IP is the socket address; `X-Forwarded-For` is ignored, so behind a reverse proxy all clients share the proxy's IP.
- Both routes exist only under this strategy (`404` otherwise).
- Sessions live in `auth_sessions`, keyed by the SHA-256 of the cookie token, and expire `CM_AUTH_SESSION_TTL` after login (no sliding renewal). An expired session is a 401 and is deleted; logins purge other expired rows.
- Password hashes live in `user_passwords` (one row per user, cascading with `users`), never in `users` and never in a response. Format `scrypt$N$r$p$salt$hash` from `node:crypto` scrypt (N=2^17, r=8, p=1, OWASP's baseline), so there is no native hashing dependency; verification reads the parameters from the stored hash, so they can be raised later.
- Setting the admin password: start the daemon with `CM_ADMIN_PASSWORD` (8 to 1024 characters). A different value replaces the hash and signs the admin out everywhere; the same value is a no-op, so leaving it set does not log you out on restart. It can be removed after the first start since the hash persists. Inside the daemon, `setUserPassword(db, userId, password)` does the same for any user.
- With `CM_AUTH_STRATEGY=password` and no admin password stored, the daemon refuses to start.

### Adding a strategy

1. Add its name to `AUTH_STRATEGY_NAMES` in `packages/shared/src/auth.ts`.
2. Add a branch for it to `AuthConfig` and `resolveAuthConfig` in `src/auth/config.ts` with any settings it needs.
3. Implement `AuthStrategy` (`name`, `resolve(c)` returning an `Actor` or `null`, optional `publicPaths`, optional `routes()` mounted under `/auth` for endpoints such as login) using `findActorById` / `findActorByUsername`, and return it from `createAuthStrategy` in `src/auth/strategy.ts`.

`createApp` defaults to the development strategy, so tests only pass `auth` when they exercise another one.

## Capabilities

A capability's server-side manifest is its only declaration. Types (`CapabilityManifest`, `Rung`, `ViewManifest`, `ToolManifest`, `NONE_RUNG`, `MANIFEST_ID_PATTERN`) live in `@candy-mountain/shared` (`capabilities.ts`). The shared package fixes no list of capability, module, plugin type, session family or activity event type ids: each is a string that must match `MANIFEST_ID_PATTERN`, be unique among what `startPlatform` registers and exist wherever it is referenced, and a violation stops boot naming the offender (see `src/boot-ids.test.ts`).

To add one, write `src/<capability id>/manifest.ts` exporting `defineCapability({...})`, list its definition in `capabilityDefinitions` (`src/definitions.ts`) and add its id to the product configuration's `capabilities`. `defineCapability` checks the manifest on import (ladder starts at `none`, which grants nothing; each rung grants at least the views, tools, tool scopes and chat of the rung below; rungs only reference the manifest's own views and tools; chat needs an agent). `startPlatform` then builds the registry before touching the data directory, re-checking each manifest plus uniqueness of capability, agent, tool, job and view ids and view paths across manifests, and that every required plugin type is registered. Any failure throws `CapabilityManifestError` naming the capability and the problem, and the daemon does not start. An agent's `family` must be a registered session family (registered by the definitions that run them, plus `PlatformOptions.families`; `src/threads/families.ts`), else `SessionFamilyError`.

The registry is `platform.capabilities` and `c.var.capabilities` in routes: `list()`, `byId(id)` (or `undefined`), `get(id)` (throws), `has(id)`. Tests use `fixtureCapability(id)` and `cloneManifest()` from `src/capabilities/fixtures.ts` with `createCapabilityRegistry([...])` or `startTestPlatform(dir, { capabilities: [...] })`.

## Modules and grants

Modules are declared in `src/modules/definitions.ts` (`MODULES`): `issues`, `agent-hub`, `operations`. Each lists member capabilities as `{ capabilityId, defaultRung }`; a capability may sit in several modules and an empty module is valid. `startPlatform` checks them against the capability registry before touching disk (member registered, default rung on its ladder, no duplicates) and refuses to boot with `ModuleDefinitionError`. The registry is `platform.modules` and `c.var.modules`: `list()`, `byId()`, `get()`, `has()`, `withCapability(id)`.

Grants live in `role_grants`, one row per role and target (`module` or `capability`), with a rung per capability (`src/grants/`, wire types in `grants.ts`). A module grant stores every member's rung; a member missing from a stored grant (added to the module later) gets its default rung. Rows cascade with the role.

`resolveActorRungs({ db, capabilities, modules }, actor)` (pass `c.var` in a route) returns the rung of every registered capability: the admin role gets the top of every ladder without reading grants; anyone else gets the highest rung across all grants of all their roles; anything ungranted, unknown or stale is `none`; any error resolves everything to `none`. `rungOf(rungs, id)` reads one capability, defaulting to `none`.

On every start `seedAdminGrants` gives the admin role a grant on each module it has none for, at each member's top rung; existing grants are never overwritten.

Admin-only REST under `/grants` (403 `forbidden` for anyone else):

- `GET /grants` -> `{ grants: RoleGrant[], roles: { role, name, rungs }[] }` with each role's resolved rungs.
- `PUT /grants` with `{ role, target: { kind, id }, rungs }` -> `{ grant }`, creating or replacing that role's grant on the target. A capability grant names exactly its own capability. Errors: `invalid_request` 400, `role_not_found`, `target_not_found`, `invalid_rung` 422.

Guard any other admin-only route with `app.use(requireAdmin())` from `src/auth`.

A manifest's optional `everyoneRung` is a rung every signed-in actor holds without any grant (the platform agent uses `chat`); the resolver applies it before grants, so grants can raise a role above it but never below, and the admin still resolves to the top rung. `assertCapability` requires it to be a ladder rung other than `none`.

## Project modules

Each project enables its own modules; a new project has none. Rows live in `project_modules` (unique per project and module, cascade with the project; `src/project-modules/`). `listEnabledModules(db, projectId, modules?)` returns the enabled ids in module registry order, leaving out modules the registry no longer has (by id when no registry is passed), and `setEnabledModules(db, projectId, moduleIds, modules?)` replaces the set and returns it.

Admin-only REST (403 `forbidden` for anyone else):

- `GET /projects/:slug/modules` -> `{ modules: ModuleId[] }`.
- `PUT /projects/:slug/modules` with `{ modules }` -> `{ modules }`, replacing the set. Errors: `invalid_request` 400, `not_found` 404, `module_not_found` 422 (id not in the module registry; nothing is changed).

## Registry

`GET /projects/:slug/registry` (any signed-in actor; 404 `not_found` for an unknown slug) answers for the current actor and one project with a `RegistryResponse` (`@candy-mountain/shared` `registry.ts`): the sidebar `groups` (one per enabled module with something to show, one per standalone capability, then the fixed system group last), every `views` entry the actor's rung shows with its absolute web route (`projectViewRoute(prefix, slug, path)`: `/<prefix>/<slug>` for the home path `''`, else `/<prefix>/<slug>/<path>`, where `prefix` is the product's `scope.urlPrefix`, `p` for Candy Mountain), the `agents` the actor may chat with, each granted `capabilities` entry with its rung, readiness and reasons, and the `degraded` modules with reasons. Code is in `src/registry/`: `computeRegistry(input)` is pure over plain data, `loadRegistry(c.var, actor, project)` gathers that input, taking the prefix from `c.var.scopeUrlPrefix`.

A capability is a candidate for a project when it belongs to an enabled module, or to no module at all (standalone). It is ready when every plugin type in `requiresPlugins` resolves to an instance for the project (`resolvePluginInstance`: its own, else a global one) whose required secrets are set and whose stored health is healthy (never tested counts as not ready), and every fact in the manifest's optional `requiresProjectFacts` (`hasBeads`, `isGitRepo`, `hasRemote`, from the project's stored verification) holds. A manifest may also name `requiresPlatformFacts` (`llmGateway`: the gateway base URL, key and model id are all set in the platform settings), which is the same answer for every project and actor; its reason has `kind: 'platform-fact'`. A module is degraded when any member is not ready. The admin sees unready views in the sidebar with the group flagged `degraded` and reasons in `capabilities[].reasons` and `degraded`; other roles get only ready entries in `groups` and `agents`, unready views still listed in `views` with `ready: false`, and no reasons.

Gate routes and tools with `gateView` / `gateTool` / `gateChat(c.var, actor, project, capabilityId, ...)`: each returns `{ allowed: true, rung, scope? }` or `{ allowed: false, code, reason, status }` (`capability_unknown` 404, `not_enabled` 404, `not_granted` 403, then `not_ready` 409; reasons name plugins only for the admin). `requireCapability({ capability, view | tool | chat })` is the Hono middleware form for a `/projects/:slug/...` route, answering with the error body.

## Activity events

`activity_events` (`src/activity/`) is the per-project feed that the Overview and notifications read; rows cascade with the project. Only the daemon writes: call `appendActivityEvent(db, { projectId, type, title, link?, payload? })` (type must be registered: `ACTIVITY_EVENT_TYPES` in `src/activity/types.ts` by default, `PlatformOptions.activityEventTypes` otherwise, else `ActivityEventTypeError`; `link` an in-app path, `payload` a JSON object capped at 4096 bytes, else `ActivityError` `payload_too_large`). There is no HTTP route that creates events.

`GET /projects/:slug/activity?type=&limit=&before=` -> `{ events, nextCursor }`, newest first. `limit` is 1 to 200 (default 50); pass `nextCursor` as `before` for the next older page (null when done). Errors: `invalid_request` 400 (bad type, limit or cursor), `not_found` 404.

## Plugin types

A plugin type is code in `src/plugins/types/<plugin type id>.ts`, exported via `definePluginType({...})` and added to `PLUGIN_TYPES` in `src/plugins/types/index.ts`, unless a capability definition brings it in its `pluginTypes` (`claude-code` comes with chat-claude-code; `startPlatform` registers both and refuses a type both the product and a definition supply). A type declares `name`, `description`, `reach` lines (what the platform can do with it, shown before enabling), `scopes` (`project`, `global` or both), `singleInstance` (at most one instance per project, or per platform for global), `configFields` (`string`, `select` or `boolean`, checked with `validatePluginConfig`), `secretFields` (names only; values live in the secrets store), and `healthCheck({ config, secrets, signal, instance?, paths? })` returning `{ healthy: true }` or `{ healthy: false, reason }`. `config` and `secrets.get(name)` are typed from the declared fields; `instance` (`{ id, scope, projectId }`) and `paths` (`DataPaths`) are present when the check runs for a stored instance through `testPluginInstance` (pass `paths` in its deps; `c.var` and `Platform` have it) and absent from a bare `checkPluginHealth` call, so a type that keeps per-instance state on disk must handle their absence.

`startPlatform` builds the registry (`platform.pluginTypes`: `list()`, `ids()`, `byId()`, `get()`, `has()`) before touching disk and refuses to boot with `PluginTypeError` on a bad or duplicate type, or with `CapabilityManifestError` when a capability's `requiresPlugins` names a type that is not registered.

Health checks get secrets through `createPluginSecrets(platform.secrets, instanceId, type)`, which reads only that instance's declared secrets (owner `plugin:<instance id>`, see `pluginSecretOwner`); never hand it or the full store to routes. Run checks with `checkPluginHealth(type, { config, secrets })`: it never throws, times out after 15 s (aborting `signal`), and redacts any secret value the check read from the reason. Tests use `fixturePluginType(id)` and `clonePluginType()` from `src/plugins/fixtures.ts`.

### Repository

`repository` (project scope, single instance) connects a project to GitHub or Bitbucket Cloud. Config: `host` (`github` | `bitbucket`), `owner` (GitHub user/org or Bitbucket workspace), `repo`, optional `defaultBranch` (overrides the host's); secret: `token` (GitHub fine-grained token, or a Bitbucket repository/workspace access token, sent as a bearer). Healthy means the token can read the repository and list its branches (and the configured default branch exists). Features reuse it through `createRepositoryOperations(repositoryConfig(instance.config), createPluginSecrets(platform.secrets, instance.id, repositoryPluginType), { signal })` from `src/plugins/repository`: `listBranches({ limit })` (most recent first, 1..100, default 30, one page), `fileExists(path, branch)`, `branchExists(branch)` and `getDefaultBranch()`. Failures throw `RepositoryHostError` (`code`, host `status`, `retryAfterSeconds`) with the token redacted; nothing retries. `listRepositoryBranches(operations, limit)` returns the `RepositoryBranchList` wire shape from `@candy-mountain/shared`. Tests stub `fetch` with `stubHosts()` from `src/plugins/repository/fake-hosts.ts`.

### Heroku

`heroku` (project scope, single instance) connects a project to one Heroku app. Config: `appName`; secret: `apiKey` (a Heroku API key or authorization token, sent as a bearer). Healthy means `GET /apps/{appName}` succeeds with the key. Features reuse it through `createHerokuOperations(herokuConfig(instance.config), createPluginSecrets(platform.secrets, instance.id, herokuPluginType), { signal })` from `src/plugins/heroku`: `getApp()` (`{ id, name, webUrl }`) and `getCurrentRelease()` (`{ version, commitSha, description, createdAt, appUrl, status }`, or `null` before the first release; the release Heroku marks `current`, so a failed newer release is skipped; `commitSha` comes from the release's slug or OCI image and is `null` when the build carried none). Failures throw `HerokuApiError` (`code`, `status`, Heroku's `herokuError` id, `retryAfterSeconds`) with the key redacted; nothing retries.

### Netlify

`netlify` (project scope, single instance) connects a project to one Netlify site. Config: `siteId` (the site's API ID, or its netlify.app domain); secret: `token` (a Netlify personal access token, sent as a bearer). Healthy means `GET /api/v1/sites/{siteId}` succeeds with the token. Features reuse it through `createNetlifyOperations(netlifyConfig(instance.config), createPluginSecrets(platform.secrets, instance.id, netlifyPluginType), { signal })` from `src/plugins/netlify`: `getSite()` (`{ id, name, url, adminUrl }`) and `getCurrentDeploy()` (`{ id, state, commitSha, branch, deployedAt, deployUrl }`, or `null` before the first published deploy; the site's `published_deploy`, falling back to the newest ready production deploy; `commitSha` and `branch` are `null` for deploys made without a commit). Failures throw `NetlifyApiError` (`code`, `status`, `retryAfterSeconds`) with the token redacted; nothing retries.

### Claude Code

`claude-code` (project scope, single instance) is the Claude account a project's agent sessions run on, so different projects can use different accounts. Each instance owns a private config directory `<data dir>/agent-homes/claude-code/<instance id>` (0700, `claudeConfigDir(paths, instanceId)` in `src/plugins/claude-code`) that is passed to the CLI as `CLAUDE_CONFIG_DIR`; the platform stores no credential beyond what the CLI writes there. Config: `authMode` (`login` by default, or `token`), optional `claudePath` (absolute path of the `claude` executable; blank means the one on PATH). Secret: `oauthToken`, the long-lived token from `claude setup-token`, used only in token mode and injected as `CLAUDE_CODE_OAUTH_TOKEN`. The CLI always gets a curated environment (PATH, HOME, locale, TERM, TMPDIR and the config dir; API keys and gateway variables never reach it).

Configuring means logging in, through three POST actions on the instance:

- `start-login` -> `{ attemptId, url, expiresAt }`: runs `claude auth login --claudeai` in the config directory, captures the sign-in link from its output and leaves the process waiting for the code. Calling it again while an attempt is open returns the same attempt. 409 `claude_code_login_failed` in token mode; 502 with a fixed reason when the CLI shows no link.
- `submit-code` with `{ attemptId, code }` -> `{ attemptId, status: 'logged_in' }` or `{ attemptId, status: 'failed', reason }`: writes the pasted `<code>#<state>` to the waiting process's stdin (never stored), waits for it to exit and confirms with `claude auth status --json`. 400 `claude_code_invalid_code` for anything without both halves (the attempt stays open), 404 `claude_code_attempt_not_found` for an unknown attempt or another instance's, 409 `claude_code_attempt_not_waiting` once the attempt ended.
- `revoke` -> `{ directoryRemoved, tokenCleared }`: ends any open attempt, deletes the config directory and clears the stored token.

`submit-code` (whatever the outcome) and `revoke` store a fresh health check before they respond, so the panel reads `instance.health` without calling `/test`. Deleting the instance or its project ends any open attempt and deletes the config directory.

Attempts live in memory in `claudeLoginAttempts` (`LoginAttemptRegistry`), expire ten minutes after they start (the process is ended and the attempt forgotten) and are all killed by `Platform.close`.

Healthy means `claude auth status --json` in the config directory reports `loggedIn: true` (with the token injected in token mode); in login mode a missing directory is "not logged in" without running the CLI. Health is only ever checked on demand (`POST /plugins/:id/test`, or at the end of the login actions above) and read from the stored result: never run it right before a session, because the status command can hold the CLI's OAuth refresh lock. A session launcher calls `claudeCodeLaunchContext(deps, projectId)` instead, which returns `{ instance, config, configDir, command, env }` (`env` holds `CLAUDE_CODE_OAUTH_TOKEN` in token mode) without touching the CLI, and treats the session's own auth-required error as the signal that the login is missing. Tests run a fake CLI from `src/plugins/claude-code/test-support/fake-claude.mjs` placed on PATH.

### Codex

`codex` (project scope, single instance, no secrets) logs the Codex CLI in with a device code. Each instance owns a private home, `<data dir>/agent-homes/codex/<instance id>` (0700, see `codexHome(paths, instanceId)`), passed as `CODEX_HOME`; nothing is stored in the platform. Config: optional `codexPath` (absolute path of the CLI; default `codex` on the daemon's PATH, the same lookup as the ACP adapter's `CODEX_PATH`). Actions (code in `src/plugins/codex/`, wire types `CodexLoginAttempt`/`CodexLoginStatusResponse`/`CodexRevokeResponse` in `@candy-mountain/shared`):

- `POST /plugins/:id/start-login` runs `codex login --device-auth` in the home with a curated environment (`curateAgentEnv` plus `CODEX_HOME`, `NO_BROWSER=1`) and returns `CodexLoginAttempt` `{ attemptId, status: 'waiting', verificationUrl, userCode, startedAt, expiresAt, ... }` once it has printed them; an attempt already open for the instance is returned as is. The CLI keeps running until the browser completes (then `codex login status` confirms: `succeeded`) or ten minutes pass (`expired`); a CLI that cannot start or shows no code is 502 `codex_login_failed`.
- `GET /plugins/:id/login-status` -> `{ attempt }` (the current or last attempt since the daemon started, or `null`); the URL and code are only present while `waiting`.
- `POST /plugins/:id/revoke` ends any open attempt and deletes the home -> `{ removed }`.

The health check runs `codex login status` in the home (a missing home is "not logged in" without starting the CLI) and is only run on demand: by `POST /plugins/:id/test`, when an attempt succeeds (stored before `login-status` reports `succeeded`) and by `revoke`. Deleting the instance or its project ends any open attempt and deletes the home. Session launchers read `codexLaunchContext(platform, projectId)` -> `{ instanceId, home, command, health } | null` and use the stored health instead of probing. Attempts live in memory in `codexLoginAttempts`, ended by the chat-codex definition's close. Tests drive a fake `codex` script (`src/plugins/codex/fake-codex.ts`).

## Plugin instances

An instance is one configured connection of a plugin type, owned by a project (`scope: 'project'`) or by the platform (`scope: 'global'`). Rows live in `plugin_instances` (cascade-deleted with their project); secret values live only in the secrets store under owner `plugin:<instance id>`. Code is in `src/plugins/instances/`, wire types in `@candy-mountain/shared` (`plugin-instances.ts`).

Admin-only REST under `/plugins` (403 `forbidden` for anyone else); `GET /plugin-types` -> `{ types: PluginTypeInfo[] }` is open to any signed-in actor:

- `GET /plugins?project=<slug>` -> `{ instances }`: the project's instances, then the global ones. Without `project`: global instances only.
- `POST /plugins` with `{ type, scope, project?: <slug>, config?, secrets? }` -> 201 `{ instance }`.
- `GET /plugins/:id`, `PATCH /plugins/:id` with `{ config?, secrets? }` (config is merged over the stored one, `null` removes a field), `DELETE /plugins/:id` -> 204 (runs the type's `onDelete` hook, then deletes the row and its secrets).
- `POST /plugins/:id/test` runs the type's health check and stores the result -> `{ instance }` with `health: { healthy, detail | reason, checkedAt }`.
- `GET|POST /plugins/:id/<action>`: per-type actions (below).

Responses show secrets only as `{ <name>: 'set' | 'unset' }`. In `secrets`, a non-empty string sets a value, an omitted key or `''` leaves it untouched, and `null` clears it (not allowed for a required secret). Any real config or secret change clears the stored health. Errors (`{ error: { code, message } }`): `invalid_request` 400, `not_found`/`action_not_found` 404, `project_not_found`/`type_not_found`/`unsupported_scope`/`invalid_config`/`invalid_secrets` 422, `instance_exists` (a second instance of a single-instance type for the same project or the platform)/`secrets_locked`/`instance_changed` 409.

Deleting a project through `DELETE /projects/:slug` first calls `deleteProjectPluginInstances`, which runs each instance's `onDelete` hook, so the secrets and agent homes go too. Other daemon code finds "the project's instance of type X" with `resolvePluginInstance(platform, projectId, typeId)` (its own instance, else the global one) and reads its secrets with `createPluginSecrets(platform.secrets, instance.id, type)`.

`createApp` takes `pluginTypes`, `secrets` (the write-only view, also `c.var.secrets`) and `secretsReader` (the full store; only handed to the `/plugins` route factory, never `c.var`). Without them it uses the product's plugin types (its own and those its definitions bring) and a locked store.

### Instance actions

A type adds endpoints to its instances with `actions` on `definePluginType`:

```ts
actions: {
  'login-start': {
    method: 'POST',
    async run({ instance, config, secrets, request, signal, paths }) {
      return { started: true } // JSON with 200, or return a Response (e.g. an SSE stream)
    },
  },
},
```

It is served at `/plugins/:id/login-start` behind the same admin guard. `config`, `secrets.get()` and `secretsWriter` (`set(name, value)` / `clear(name)`, which go through `updatePluginInstance` so they validate like a PATCH and reset the stored health) are typed from the type's fields; throw `PluginActionError(status, code, message, headers?)` for an error body. `refreshHealth()` runs the type's health check and stores it exactly like `POST /test`, resolving to the stored health or `null` when the instance changed or was deleted meanwhile (nothing stored); it still works after the request has ended, e.g. from a login process's completion. `resetHealth()` clears the stored health. Names are lowercase letters, digits and dashes; `test` is reserved. The Repository type's `branches` action is the example: `GET /plugins/:id/branches?limit=N` -> `RepositoryBranchList`, mapping `RepositoryHostError` to `repository_<code>` (`no_token` 409, `rate_limited` 503 with `Retry-After`, the rest 502).

A type that keeps per-instance state outside the database (an agent home) cleans it up with `onDelete({ instance, paths, secrets })`. It runs before the row and secrets are deleted, for `DELETE /plugins/:id` and for a project delete; if it throws, the instance stays.

## Bots

A bot is a Slack-facing agent for one project: one row in `bots` (cascade-deleted with the project), code in `src/bots/`, wire types in `@candy-mountain/shared` (`bots.ts`). Fields: `name` (unique per project, ignoring case), `family` (`claude-code` | `codex`), `writeScope` (`read-only` default, `write-confirm`, `write-auto`), `baseBranch` (null = the Repository plugin's default branch), `personaName`, and `answersIn` (`{ anywhere: true }` default, or `{ channels: ['C0123ABCD', ...] }`). The Slack bot token (`xoxb-`) and app-level token (`xapp-`) live in the secrets store under owner `bot:<id>` as `slackBotToken` and `slackAppToken`.

Admin-only REST (403 `forbidden` otherwise), since bots hold Slack credentials:

- `GET /projects/:slug/bots` -> `{ bots }` (by name); `POST /projects/:slug/bots` with `CreateBotRequest` -> 201 `{ bot }`.
- `GET`, `PATCH` (any create field; omitted fields stay) and `DELETE` (204, also deletes its secrets) on `/projects/:slug/bots/:id`.

Saving needs the Repository plugin configured for the project (422 `repository_not_configured`), and choosing a family (on create or when it changes) needs that family's plugin to have a stored healthy test result (422 `family_unavailable`). Secrets follow the plugin instance rules: a non-empty string sets, omitted or `''` leaves, `null` clears; a value while the store is locked is 409 `secrets_locked`. Other errors: `invalid_request` 400, `not_found` 404, `invalid_secrets` 422 (unknown name or wrong prefix), `name_taken` 409.

Every read returns `baseBranch` as saved plus `effectiveBaseBranch`, resolving a blank one through the Repository plugin's `getDefaultBranch()` at read time (null, with a warning, when that fails), and `status` from `computeBotStatus`: `active` (family plugin healthy, persona verified, both keys set), `not_configured` (no Slack key and the persona not verified), else `{ warnings }` listing each reason. Changing the persona name, family or base branch resets the persona to `unverified`; the persona check stores its result with `recordBotPersonaCheck(db, id, updatedAtWhenStarted, { status: 'verified' | 'missing', reason })`. Daemon code reads bots with `listBots({ ...platform, secretsReader: platform.secrets }, { projectId? })` and their tokens with `createBotSecrets(platform.secrets, botId)`; the bots definition's `onWorkspaceDeleted` hook calls `deleteProjectBots` before `DELETE /projects/:slug` removes the row. The definition also checks at start that every `BOT_FAMILIES` entry is a registered session family.

Persona check (`src/bots/persona.ts`): the persona lives in the repository as `.claude/agents/<name>.md` (Claude Code) and `.agents/<name>.md` (Codex) on the bot's effective base branch, looked up through the Repository plugin's host API (10 s timeout), never a checkout.

- `POST /projects/:slug/bots/:id/check-persona` -> `BotPersonaCheckResponse` `{ branch, claudeCode, codex, checkedAt, status, reason, bot }`. Both families are reported; only the bot's own family is recorded (`verified`, or `missing` with a reason naming the file and branch, which becomes the status warning). A missing base branch is recorded as `missing`; any other host failure is 502 `persona_check_failed` and records nothing. No persona name is 422 `persona_not_set`.
- `POST /projects/:slug/bots/check-persona` with `{ personaName, baseBranch? }` -> `{ branch, claudeCode, codex }` for an unsaved bot; records nothing.
- `assertBotPersonaBeforeSession(readDeps, bot)` re-runs the check before a bot session starts and throws `BotPersonaMissingError` (`code: 'persona_missing'`, `path`, `branch`, `family`) when the bot's family has no file.

## Bot sessions

`src/bot-sessions/` runs a bot the way Slack and the console both need: the bots definition (`src/bots/definition.ts`, `dependsOn: ['chat-claude-code']` for the ACP session service) creates `createBotSessionService({ db, paths, pluginTypes, secrets, secretsReader, sessions, worktrees })` and offers it as `BOT_SESSIONS` (which the same definition hands the Slack router, decisions and handoffs; see Slack routing) and as the platform-owned `THREAD_BOTS` (`src/threads/bots.ts`), through which the thread service runs bot threads.

`botSessions.start({ botId, holder, actorId, signal? })` -> `{ bot, session, lease, thread, resumed, neutralised, warnings }`. The holder is `{ kind: 'console', id: <chat thread id> }` or `{ kind: 'slack', id: <thread key the Slack surface chooses> }`. If the holder already has a session whose worktree lease is still active, that session and lease are resumed (`resumed: true`, `worktrees.resume` touches the lease). Otherwise, in order: the bot is re-read (`getBot`), its family plugin must be stored healthy, `assertBotPersonaBeforeSession` re-checks the persona on the base branch, a session id is drawn, `worktrees.acquire({ holder: { kind: 'session', id }, baseBranch: bot.effectiveBaseBranch, branchName: botBranchName(bot.name, id) })` cuts the worktree (and installs dependencies), the persona text is read from the worktree (`.claude/agents/<name>.md` / `.agents/<name>.md`; `--agent` reads the same file), `surfaceInstructionsForBot` composes the platform text (branch, base, dependency state, whether bd is connected), `resolveBotPosture` maps the write scope with both the worktree and the main checkout vetted, `beadsEnvForWorktree(main checkout)` gives `BEADS_DIR` / `BD_NON_INTERACTIVE`, `assertPostureNotWidened` runs once more on the exact flags, env and codex options handed over, and `sessions.create({ id, cwd: lease.path, posture, bot })` writes the row and a `session.started` activity event titled `Bot "<name>" session started` (payload adds `botId`, `botName`). The posture JSON carries `flags` (Claude) or `codex` (Codex) as before, plus `env` (reused by the launcher on every resume; never settable over REST) and `bot: { id, name, holder }`, which is how a holder finds its session again (`json_extract` on the column; no new table). A failure after the worktree exists releases it. For a console holder the thread row is written here with `agentId: 'bot:<bot id>'` (`botAgentId`), title the bot name, model and effort null; starting the same thread again after its session was closed switches it to the new session (`chat_thread_sessions` keeps the history). The `/threads` routes serve these threads as `bot:<bot id>` agents (see Chat threads); the thread service adopts a thread it did not create (or whose session changed) on the next read, so its `working`/`unread` flags follow. Stream and answer decisions through the session routes on `session.id` (gated on the bot family's Agent Hub chat capability).

Sandboxes: with a `.beads` in the main checkout, Claude's write-auto sandbox gets `beadsDir` in `filesystem.allowWrite` next to the package-manager stores (bd itself is excluded from the sandbox, so this covers its helpers). Codex write-confirm and write-auto bots get `beadsDir` as `codex.writableRoots` (`resolveBotPosture({ beadsDir })`), so bd writes from the `workspace-write` sandbox need no escalation; read-only bots get none.

`botSessions.prompt(sessionId, text)` resumes the lease (so `last_used_at` moves and the reclaimer leaves the worktree alone; a released lease is `worktree_released`) and sends the turn. Prompts that arrive on the plain session routes are covered too: the service observes every session and touches the lease of a bot session on each `prompt` row. `botSessions.close(holder)` / `closeSession(sessionId)` cancel a running turn and call `worktrees.release(lease.id)` under the safe-reclaim rule: `{ session, lease, released, keptUnpushed }`, where `keptUnpushed` means the worktree stayed because of uncommitted or unpushed work (`lease.unpushedReason`); the branch is always kept and the idle live process is left to the session reaper. `find(holder)` returns the newest session for the holder.

Failures are `BotStartError` (`reason`, `status`): `persona_missing` 422 (no persona name, or the file is missing on the base branch or in the worktree), `persona_check_failed` 502, `plugin_unhealthy` 422, `repository_not_configured` 422, `worktree_cap` 409, `worktree_failed` 502 (fetch, base branch, clone), `worktree_released` 409 (prompting after the lease went), `posture_refused` 422 (`PostureError`). `dependencies_failed` is never thrown: it comes back in `warnings` and the agent's instructions say so.

Console REST (admin only, under `/projects/:slug/bots/:id`): `POST /sessions` `{ threadId? }` -> 201 `{ session, lease: { id, path, branch, baseBranch, dependencies, unpushedWork, unpushedReason }, thread, resumed, warnings }` (200 with `resumed: true` when `threadId` names a thread that still holds a session; a new thread id is generated otherwise); `POST /sessions/:sessionId/close` -> `{ session, lease, released, keptUnpushed }` (idempotent; `lease: null` once released). Errors use the `BotStartError` reason as the code.

## Team roster

`src/team/` keeps who may talk to a project's bots (`team_members`: `id`, `project_id` cascade, `display_name`, `email` nullable, `slack_member_id` unique per project, `bot_scope` JSON `{ all: true }` | `{ botIds: string[] }`, `last_active_at`, timestamps). Sessions run under the project's plugin login, so there is no per-person agent login. Admin only: `GET`/`POST /projects/:slug/team` and `GET`/`PATCH`/`DELETE /projects/:slug/team/:id` (`TeamMember`, `CreateTeamMemberRequest`, `UpdateTeamMemberRequest`; an omitted `botScope` on create is `{ botIds: [] }`). Errors: `invalid_request` 400, `not_found` 404, `slack_member_taken` 409, `unknown_bot` 422 (a scope id that is not a bot of this project).

- `mayMemberTalkToBot(db, projectId, slackMemberId, botId)` -> boolean for Slack routing; false for an unlisted member, a bot outside the scope, or a removed member.

## Uptime monitors

`src/uptime/` keeps a project's monitors as rows (`uptime_monitors`: `id`, `project_id` cascade, `name`, `source_type`, `target` URL, `interval_seconds`, `enabled`, `options` JSON, timestamps). Intervals are whole seconds from `MONITOR_INTERVAL_MIN_SECONDS` (30) to `MONITOR_INTERVAL_MAX_SECONDS` (86400), default 60; targets are absolute http(s) URLs.

A monitor source type is declared with `defineMonitorSource({ id, label, description, targetLabel, targetPlaceholder?, fields })` in `src/uptime/builtin-sources.ts` and added to `MONITOR_SOURCES`; `MONITOR_SOURCE_REGISTRY` (`list()`, `ids()`, `byId()`, `get()`, `has()`) is built when the module loads, so a bad or duplicate source (`MonitorSourceError`) stops the daemon at boot. Option fields are `string` (`pattern`, `maxLength`) or `integer` (`min`, `max`), each with `required` / `default`, checked by `validateMonitorOptions` from `@candy-mountain/shared`; the stored options are its normalised output (strings trimmed, defaults filled). Built in: `http` (`expectedStatus` default 200, optional `responseContains`), `statuspage` (`componentId`; target is the page's `/api/v2/components.json`), `statusio` (`componentId`, `containerId`; target is `https://api.status.io/1.0/status/<page id>`) and `statping` (`serviceId`; target is the page's `/api/services`).

The `uptime` capability (Operations module; ladder none, read, manage) gates every project monitor route: reads need its `uptime` view, writes need the admin and the `uptime.manage` tool. `GET /monitor-sources` stays open to any signed-in actor.

- `GET /monitor-sources` -> `{ sources: MonitorSourceInfo[] }` in registration order.
- `GET`/`POST /projects/:slug/monitors` -> `{ monitors }` (by name) / 201 `{ monitor }` from `CreateMonitorRequest` `{ name, sourceType, target, intervalSeconds?, enabled? (true), options? }`.
- `GET`/`PATCH`/`DELETE /projects/:slug/monitors/:id`: omitted fields are unchanged, `options` replaces the stored options whole, and changing `sourceType` without `options` validates `{}` against the new type.
- `POST /projects/:slug/monitors/:id/enable` and `/disable` -> `{ monitor }`.

Errors: `invalid_request` 400 (shape, name, target, interval), `not_found` 404 (also a monitor of another project), `unknown_source` 422, `invalid_options` 422 (message lists each `field: problem`). Service: `listMonitors`, `listEnabledMonitors` (all projects that are not archived), `findMonitor`/`getMonitor`, `createMonitor`, `updateMonitor`, `setMonitorEnabled`, `deleteMonitor`, `monitorSourceOf`.

Checks: every source has `check(context)` (`MonitorCheck`, `src/uptime/check.ts`), and `assertMonitorSource` refuses a source without one, so a missing checker stops the daemon at boot. `runMonitorCheck(monitor, { sources?, signal?, fetch?, timeoutMs? })` runs one check now (no scheduling) and never rejects. The result is `MonitorCheckResult` `{ ok, status: 'up' | 'degraded' | 'down', httpStatus, detail, latencyMs, checkedAt }`: `ok` is `status === 'up'`, `httpStatus` is null when nothing answered, and `detail` says why it is not up without the response body or the target URL (credentials in the target are redacted). It is one check's own verdict; hysteresis across checks is the caller's. The built-in checks share `probe`: a GET with `redirect: 'manual'`, a `MONITOR_CHECK_TIMEOUT_MS` (5 s) timeout covering the body, bodies capped at 2 MB, and up to 5 redirects followed only on the target's host (http may upgrade to https); a timeout, DNS failure, refused connection, bad JSON or a redirect elsewhere comes back `down`, and a caller's aborted `signal` comes back `down` with `Check cancelled.`.

- `http`: up when the status equals `expectedStatus` and, if set, the body contains `responseContains`; a 3xx `expectedStatus` is compared without following.
- `statuspage`: reads `components[]` (from `/api/v2/components.json` or `/api/v2/summary.json`) for `componentId`: `operational` and `under_maintenance` up, `degraded_performance` and `partial_outage` (and unknown statuses) degraded, `major_outage` down.
- `statusio`: reads `result.status[]` for `componentId`, then its `containers[]` for `containerId`: `status_code` 100 and 200 (maintenance) up, 300 and 400 degraded, 500 and above down.
- `statping`: reads the `/api/services` list or a single `/api/services/<id>` for `serviceId`: `online` up, otherwise down with the last success time.

A vendor feed that answers non-2xx, is not JSON, has another shape or lacks the component is down.

Scheduling: the uptime definition (`uptimeDefinition(options)`, `src/uptime/definition.ts`) starts the scheduler (`startUptimeScheduler({ db, key?, ownerFile?, sources?, fetch? }, { historyMax?, historyMaxAgeMs?, timeoutMs?, staggerWindowMs? })`, `src/uptime/scheduler.ts`), which loads every enabled monitor and gives each its own timer. A monitor's next check is due `interval_seconds` after its last stored check, so a restart keeps the cadence; one with no history (or overdue) is checked within `MONITOR_STAGGER_WINDOW_MS` (15 s), offset by a hash of its id so monitors do not all fire at once. The service emits `onMonitorChange(listener)` (`{ kind: 'saved', monitor }` or `{ kind: 'deleted', monitorId }`, with the db written to) after every create, update, enable, disable and delete, and the scheduler reschedules on it without a restart: a new interval counts from the last check, a changed target, type or options cancels any in-flight check and checks again soon, and disable or delete stops the timer. Each tick re-reads the monitor, so one removed another way (its project deleted) is dropped. A tick that finds the previous check still running is skipped, so a slow check never overlaps the next. Checks the scheduler cancelled itself (edit, delete, close) are discarded, everything else is stored in `uptime_checks` (`id`, `monitor_id` cascade, `checked_at` (check start, ISO), `ok`, `status`, `http_status`, `latency_ms`, `detail`; indexed on monitor + time) and then pruned to `CM_UPTIME_HISTORY_MAX` rows and `CM_UPTIME_HISTORY_MAX_AGE` per monitor. Only one scheduler polls a data directory: starting another in the same process closes the first, and the newest writes its token to `run/uptime-scheduler.owner`, so an older process still shutting down stops at its next tick. `scheduler.onCheck(({ monitor, check }) => ...)` is called after each check is stored; `listMonitorChecks(db, monitorId, limit = 50)` (max 1000) reads stored checks newest first. Monitors of an archived project are paused: `listEnabledMonitors` and the per-tick re-read (`findPolledMonitor`) skip them, and `onProjectArchiveChange` (from `src/projects/projects.ts`) makes the scheduler reload on archive and unarchive.

State and incidents: `deriveMonitorState(checks)` (`src/uptime/state.ts`, checks newest first) is `down` when the newest `MONITOR_DOWN_THRESHOLD` (3) checks all have status `down`, `degraded` when any of those three is not `up` or took over `MONITOR_SLOW_LATENCY_MS` (2000), `up` otherwise and `unknown` with no history, so after an outage it reads degraded until three good checks in a row. State is never cached: it is derived from stored checks on every read, so a restart rebuilds it for free. the uptime definition starts the incident tracker (`startIncidentTracker({ db, scheduler, scopeUrlPrefix })`), which calls `reconcileMonitorIncident(db, monitor, scopeUrlPrefix)` after every stored check and once per polled monitor at boot: down with no open incident opens one, up with one open closes it, anything else changes nothing (an incident stays open while the monitor is degraded or disabled). Because it compares against the `uptime_incidents` rows rather than a remembered previous state, a restart opens no second incident, and a partial unique index on `monitor_id` where `closed_at` is null holds one open incident per monitor even across processes. `uptime_incidents`: `id`, `project_id` and `monitor_id` (cascade), `opened_at` and `closed_at` (the `checked_at` of the check that tipped the state), `reason` (that check's `detail`), `thread_id` (nullable chat thread for a later investigation, set null on thread delete; only `setIncidentThread` writes it, nothing investigates automatically). Opening appends `incident.opened` (title `<name> is down: <reason>`, payload `{ incidentId, monitorId, monitorName, reason, openedAt }`) and closing appends `incident.closed` (title `<name> is back up`, payload `{ incidentId, monitorId, monitorName, openedAt, closedAt, durationMs }`), both linking to `uptimeMonitorLink(prefix, slug, monitorId)` = `/<prefix>/<slug>/uptime?monitor=<id>`.

Reads, open like the other monitor reads:

- `GET /projects/:slug/monitors/:id/status?recent=` -> `{ status: MonitorStatus }` = `{ monitor, state, lastCheck, openIncident, recentChecks }`; `recent` 0 to 200, default 30, newest first.
- `GET /projects/:slug/monitors/:id/checks?limit=` -> `{ checks }` newest first; `limit` 1 to 1000, default 50.
- `GET /projects/:slug/monitors/:id/incidents?status=open|closed&limit=` and `GET /projects/:slug/uptime/incidents?status=&limit=&monitor=` -> `{ incidents }` newest opened first; `limit` 1 to 200, default 50.
- `GET /projects/:slug/uptime/status?recent=` -> `{ monitors: MonitorStatus[] }` for every monitor of the project (by name), so the Uptime page needs one request per refresh.

A bad `recent`, `limit` or `status` is `invalid_request` 400; an unknown monitor (also in `?monitor=`) is `not_found` 404.

## Environments and live versions

`src/environments/` keeps a project's environments as rows (`environments`: `id`, `project_id` cascade, `name` unique per project ignoring case, `live_source_kind`, `live_source_settings` JSON, `deploy_kind` / `deploy_settings` nullable and unused until deploy strategies land, timestamps). Each environment names a live-version source that fills the common `LiveVersion` shape (`version?`, `branch?`, `deployedAt?` ISO 8601, `link?` absolute http(s)); every answer passes through `normaliseLiveVersion`, so a source cannot put anything else on the wire.

A source is declared with `defineLiveVersionSource({ id, label, description, fields, validate?, read })` and added to `LIVE_VERSION_SOURCES` in `src/environments/builtin-sources.ts`; the deployments definition (`src/deployments/definition.ts`, `deploymentsDefinition({ sources?, fetch? })`) builds its registry in `start`, so a bad or duplicate source, or one whose `plugin` names a plugin type nothing registers, stops the daemon at boot with `LiveVersionSourceError`. The definition mounts the environment routes under `/projects` and `GET /live-version-sources`, and brings the `netlify` and `heroku` plugin types; `deploymentsRoutes(secretsReader, { sources?, fetch? })` gives the routes alone for tests. `fields` use the monitor option field kinds and `validateLiveVersionSettings`; `validate(settings, { projectId, deps })` returns `{ field, message }[]` for rules the fields cannot express (`field: ''` for the whole environment), and `deps` (`db`, `pluginTypes`, `secrets`) lets it check the project's plugins. `read({ settings, project, signal, fetch, deps })` resolves to a `LiveVersion` or throws (the message becomes that environment's error); `deps` carries `db`, `pluginTypes`, `secrets` and `secretsReader`, so a vendor source can call `resolvePluginInstance(deps, project.id, 'netlify')` and `createPluginSecrets(deps.secretsReader, instance.id, type)`. Each read is cut off after `LIVE_VERSION_READ_TIMEOUT_MS` (15 s).

Built in: `custom-endpoint` (`url` plus `versionPath`, `branchPath`, `deployedAtPath`, `linkPath`, at least one path). The daemon GETs the URL with a 5 s timeout, follows redirects only on the same host (at most 5), reads at most 1 MiB of JSON and reads each path: dotted (`build.sha`, `deploys.0.sha`), bracketed (`deploys[0].meta["git.ref"]`) or with a leading `$`. A missing path leaves its field out; if none are found the read fails. Numbers become version strings, deploy times accept ISO strings or Unix seconds/milliseconds, and relative links resolve against the endpoint.

`netlify` and `heroku` (`src/environments/plugin-sources.ts`, no settings) read through the project's plugin instance of that type. Saving an environment with either kind, or switching one to it, is refused with 422 `invalid_settings` unless the instance exists and its last stored health check passed: "The Netlify plugin is not set up for this project; ...", "... has not been tested since it last changed; ..." or "The Netlify plugin is unhealthy: <the plugin's reason>". A read checks the same thing first and reports that message as the environment's error without calling the vendor, so an instance that later tests unhealthy shows its reason. Netlify maps the production deploy: `version` = commit, `branch`, `deployedAt` (published, else created), `link` = the deploy permalink (the site URL when the deploy has none); a deploy without a commit has no `version`. Heroku maps the current release: `version` = the build commit, else `v<release number>`, `deployedAt` = the release time, `link` = the app's web URL, no `branch`. A site or app that has never deployed is `{}`; vendor errors (401, 404, rate limits, unreachable) become the environment's error.

Writes are admin only; reads are open to any signed-in actor until a deployments capability gates them.

- `GET /live-version-sources` -> `{ sources: LiveVersionSourceInfo[] }`.
- `GET`/`POST /projects/:slug/environments` -> `{ environments }` (creation order) / 201 `{ environment }` from `CreateEnvironmentRequest` `{ name, liveSourceKind, liveSourceSettings? }`.
- `GET`/`PATCH`/`DELETE /projects/:slug/environments/:id`: omitted fields are unchanged, `liveSourceSettings` replaces the stored settings whole, and changing `liveSourceKind` without settings validates `{}` against the new kind.
- `GET /projects/:slug/live-versions` -> `{ environments: EnvironmentLiveVersion[] }`, one `{ environmentId, environmentName, liveSourceKind, checkedAt, live: { ok: true, version } | { ok: false, error } }` per environment, read in parallel; a failing source fails only its own entry.

Errors: `invalid_request` 400, `not_found` 404, `name_taken` 409, `unknown_source` 422, `invalid_settings` 422 (message lists each `field: problem`).

## Bot posture

`src/posture/` turns a bot's write scope into the launch the harness passes through, and refuses anything wider. `resolveBotPosture({ family, writeScope, personaName, personaText, surfaceInstructions?, checkoutDir, mainCheckoutDir?, checkoutSettings?, claude? })` returns `{ flags, env, codex?, settingsOverrides, neutralised }`: `flags`/`env` go to `startSession` for Claude Code (`codex` for Codex), `settingsOverrides` is the object inside `--settings`, and `neutralised` lists each checkout settings key the launch outranks and how. `assertPostureNotWidened(posture, writeScope)` runs inside the resolver and again wherever the result is handed to the harness; it throws `PostureError` (`code: 'widened' | 'bypass' | ...`) for a bypass token, a mode other than the scope's, a dropped guard, an editing or blanket-shell allow, or a missing denial.

Claude Code: read-only is `--permission-mode plan` with `ExitPlanMode`, `Agent` and `Workflow` denied and auto mode off during plan; write-confirm is `default` with `Agent` and `Workflow` denied; write-auto is `acceptEdits` with the Bash sandbox on and required (`allowUnsandboxedCommands: false`, `bd` excluded from it) and a `Bash(git push *)` ask rule. Every scope passes `--strict-mcp-config`, `--agent <persona>`, `--allowedTools Bash(bd *)` and an inline `--settings` with `disableAllHooks`, the bypass and auto modes disabled, and the checkout's own `.claude/settings.json` / `.claude/settings.local.json` vetted: their `permissions.allow` rules are mirrored as `ask` rules (ask outranks allow from any file), `additionalDirectories` become `Edit` denials, hooks, `defaultMode`, `sandbox`, `agent` and project MCP keys are outranked by the flags. A persona's front matter may not ask for a bypass, a `permissionMode` above the scope's, a tool the scope denies, hooks, MCP servers, an observer or out-of-scope memory. `vetCheckoutAgents(dir, writeScope)` holds every other agent file in the checkout to the same ceiling (`.claude/agents/**/*.md`, `.claude/skills/*/SKILL.md`, `.claude/commands/**/*.md`, and `.agents/*.md` when it has front matter), since a forked skill can start a subagent in its own `permissionMode` even with `Agent` denied: a bypass is `bypass`, anything wider is `checkout_agent_widens`, a block it cannot read is `checkout_agent_unreadable`, and a skill or command's `allowed-tools` approvals become ask rules (reads and `bd` excepted) listed in `neutralised`. A checkout settings file setting `env`, `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport` or `otelHeadersHelper` is refused (`checkout_settings_widens`): no override can take those back. The resolver vets both `checkoutDir` and `mainCheckoutDir` (settings too, unless `checkoutSettings` is given). Codex: read-only is the `read-only` mode, both write scopes are `workspace-write`, and the persona text plus surface instructions become `codex.developerInstructions`; given `beadsDir`, the write scopes add it as `codex.writableRoots`. The verifier refuses writable roots on read-only and any root that is not an absolute, normalised `.beads` directory.

## Slack connections

`src/slack/` keeps one Socket Mode connection per active bot, so Slack works with no public URL. The service-only `slack` capability definition (`src/slack/definition.ts`, `slackDefinition({ connections?, fetch?, web? })`: no manifest, so no views, no ladder and nothing in the catalog, modules or grants) starts it, brings the `slack` plugin type, offers the connections as `SLACK_CONNECTIONS` (`slack.connections`; the bots definition, which declares `dependsOn: ['chat-claude-code', 'slack']`, runs the router, decisions, handoffs and the status route below over them), returns the Block Kit MCP server in `mcpServers` and the Slack notification channel in `notificationChannels`, and closes every connection when the definition list closes (after the sessions that may still post). A product without the definition has no `slack` plugin type, no Slack MCP server and no notification channel, and must leave bots out too (the daemon refuses the list otherwise). It polls the `bots` table every 2 s (`SLACK_RECONCILE_MS`, or call `reconcile()` on the `SLACK_CONNECTIONS` service): a bot is connected when its project is not archived and `computeBotStatus` says `active` (the base-branch check is skipped, so a Git host outage does not drop Slack); a token change restarts its connection, and losing active status, a deleted bot or an archived project closes it. Missing keys never start anything and are reported, not thrown.

Each connection calls `auth.test` with the bot token, `apps.connections.open` with the app-level token (both through `createSlackClient`), opens the WebSocket with `ws`, and is connected on Slack's `hello`. Every envelope is acknowledged before it is dispatched. A `disconnect` envelope reconnects at once; a closed socket, a failed request or a ping unanswered for 10 s (pings every 30 s) retries after 1 s doubling to 60 s with jitter, or Slack's `Retry-After`; a rejected token retries every 5 minutes (a new token reconnects at the next poll).

- `slack.subscribe(listener, { botId?, kinds? })` -> unsubscribe. Events (`SlackBotEvent`, in `src/slack/events.ts`) carry `botId`, `projectId`, `envelopeId`, `retryAttempt`, `retryReason`, `receivedAt` and `botUserId`, and a `kind`: `app_mention` / `message` (`eventId` to dedupe on, `teamId`, `fromSelf`, `event: { channel, channelType, user, senderBotId, subtype, text, ts, threadTs, raw }`), `slash` (`command`) or `interactive` (`interaction: { type, userId, channelId, messageTs, threadTs, actions, responseUrl, triggerId, raw }`). Other event types are acknowledged and dropped. A listener that throws is logged and does not affect the others.
- `slack.status(botId)` -> `BotSlackConnection` (`@candy-mountain/shared`): `state` (`connected` | `connecting` | `disconnected`), `reason`, `reasonCode` (`missing_keys`, `inactive`, `archived`, `secrets_locked`, `invalid_token`, `error`, `stopped`), `since`, `retryAt`, `identity` (workspace and bot user).
- `slack.web(botId, options?)` -> `{ client, operations }` (`createSlackClient` / `createSlackOperations` with the bot token) or null without a bot token.
- `GET /projects/:slug/bots/:id/slack` (admin only, `botSlackConnectionPath(slug, id)`, `slackRoutes` in `src/slack/routes.ts`, mounted by the bots definition) -> `{ connection }`; 404 for an unknown project or a bot of another project.

## Slack routing

`src/slack/router.ts` turns the events above into bot sessions: the bots definition starts it after its bot session service as `startSlackRouter({ db, slack, botSessions, sessions, interceptReply? }, BotsOptions.slackRouter)` (`{ fetch?, now?, log?, acknowledgeReaction?, streamIntervalMs?, onTurnEnd? }`), offers it as `BOT_SLACK_ROUTER` and closes it before the bot session service. The router, decisions and handoffs code stays in `src/slack/` but only the bots definition starts it; a daemon without bots has no Slack routing. It only needs `slack.subscribe` and `slack.web`, so tests drive it with `createSlackEventBus()` and a recording `fetch` instead of a Socket Mode link (`src/slack/router.test.ts`).

Rules, in order, for every `app_mention` and `message` event: the bot's own posts, messages with a `subtype` (edits, joins, bot messages) and messages without a user are dropped; the delivery is claimed in `slack_deliveries` (`bot_id` + `event_id`, and unique on `bot_id` + `channel_id` + `ts`, because a mention inside a thread arrives twice under different event ids) and a claim that already exists ends it there, so a redelivered event never runs twice. A top-level message counts only when it mentions the bot (`app_mention`, or `<@botUserId>` in the text): the bot must answer in the channel (`answersIn` anywhere or the listed channel id) and the member must pass `mayMemberTalkToBot`; otherwise silence. An accepted message gets the `eyes` reaction (`reactions:write`) and stamps `last_active_at`. A new mention starts `botSessions.start({ botId, holder: { kind: 'slack', id: '<botId>:<channel>:<thread_ts>' }, actorId: 'slack:<member id>' })` and writes `slack_threads` (`project_id`, `bot_id`, `team_id`, `channel_id`, `thread_ts`, `session_id`, `slack_member_id`, `state` open | closed, `turn_count`, timestamps; unique on bot + channel + thread). A `BotStartError` is posted to the thread as is (its message already names the bot and the reason).

Replies (`thread_ts` set and not equal to `ts`) in a mapped thread continue that session with `botSessions.prompt` when both the replier and the member who opened the thread still pass the roster check; an unmapped thread, a non-member, or a thread whose opener was removed gets silence. After a restart nothing is in memory: the first reply finds the row, `prompt` resumes the session in the same worktree. A `worktree_released` (the reclaimer took it) starts a fresh session and worktree on the same thread and points the row at it. Events of one thread run one after another, so a reply sent while the mention is still cutting its worktree waits for it. The message "done" on its own (any case, with emphasis or a full stop) skips that queue: it closes the row and calls `botSessions.closeSession`, which cancels a running turn and releases the worktree under the safe-reclaim rule; the thread is told whether the worktree went or was kept with unpushed work (and why). A plain reply in a closed thread is ignored; a new mention in it starts over in a fresh worktree.

What the agent gets: the first turn is a sentence saying a Slack request arrived and that the final message is posted to the thread, then a `<slack-request>` block with `from: <display name> (<member id>)`, `channel:`, `thread:` and `message:` followed by the text; replies send the same block as `<slack-reply>` without the sentence. The text has the bot's mention removed, `<url|label>` and `<url>` unwrapped and `&amp;`/`&lt;`/`&gt;` decoded (`slackTextToPlain`). What Slack gets: the turn's progress in one message (see Slack turn progress); a start error is posted as is. Block Kit handoff cards, decision buttons and the thread-scoped MCP tool build on `findSlackThreadBySession(db, sessionId)` and the holder id above. Not handled here: `slash` events (`interactive` ones are decision buttons, see Slack decisions), DMs (no mention, so silence), mentions inside threads the bot did not open.

## Slack turn progress

`src/slack/progress.ts` (`createSlackProgress`) shows a turn in exactly one thread message, fed from the session log by the router (`text` rows with `role: 'agent'`, and `tool_call` / `tool_result` rows as summarised steps titled from the tool call). Native first: the first text or step opens `chat.startStream` (`thread_ts`, `recipient_user_id` = the member whose message started the turn, `recipient_team_id`, `chunks` of `markdown_text` and `task_update` `{ id: toolCallId, title, status in_progress | complete | error }`), later rows go out as `chat.appendStream` and the turn ends with `chat.stopStream`. A `slack_error` from `chat.startStream` other than a channel or token error (which a post would hit too) means the workspace cannot stream: the router remembers that per bot until restart and the turn posts one `chat.postMessage` instead, edited with `chat.update` (step lines `… / ✓ / ✗ title`, the text, `_Working…_` while running; at most 3,900 characters while working, overflow sent as plain replies after the final edit). Updates of one turn are at least `streamIntervalMs` apart (router option, default 1000 ms). A turn short enough to end before the first send is a single `chat.postMessage`; a turn with nothing to say and no steps posts nothing. Slack caps a stream at 10 minutes and 12,000 characters, so a stream older than 9 minutes or about to pass 11,500 characters is stopped and the same message carries on as `chat.update` edits; `message_not_in_streaming_state` does the same, and `stopped_by_user` stops all further calls for the turn. Endings: `_Stopped._` is added to a cancelled turn that already showed something, `The bot could not finish: ...` to a failed one.

Exactly once: each turn has a `slack_turns` row (migration 0020: `thread_id`, `session_id`, `slack_member_id`, `prompt_seq` = the turn's prompt row, `sent_seq` = the last log row Slack has seen, `mode` stream | message, `message_ts`, `state` open | finished | completed, `resumes`, timestamps), written at the prompt and updated after every successful Slack call. On start, before any new event, the router recovers every open or finished row on that thread's queue: a turn whose log already has its `turn_end` is ended in its message from the log; a turn still running when the daemon died is resumed once with a `<slack-resume>` prompt (`slackResumeText`) into the same message, sending only rows after `sent_seq`; a second interruption, a closed thread or a replaced session ends the message with a note instead. The message is created only when `message_ts` is empty, so a restart never posts a second one (a crash between Slack creating the message and the row being written is the one gap). A finished row (message final) runs `onTurnEnd` again.

Turn end (`SlackRouterOptions.onTurnEnd`): `({ thread, sessionId, turnId, text, outcome: completed | cancelled | failed, error, message, client }) => void | Promise<void>` runs in `end()` in `router.ts` after the message is final; the row is `finished` before it runs and `completed` after it returns or throws, so a restart in between runs it again. It must be safe to repeat: edit `message.ts` (`chat.update` with `blocks`) or key anything it posts on `turnId`. After a restart `error` is null and `outcome` comes from the log.

## Slack decisions

`src/slack/decisions.ts` puts pending decisions (see Pending decisions) of Slack-held bot sessions into their thread: the bots definition starts it as `startSlackDecisions({ db, slack, decisions, sessions }, BotsOptions.slackDecisions)` (`{ fetch?, now?, log?, answeredReaction? }`), offers it as `BOT_SLACK_DECISIONS` and passes its `interceptReply` to the router. It observes the session log: a `decision_opened` row whose session has an open `slack_threads` row posts one message (`chat.postMessage` with `thread_ts`); `decision_answered` / `decision_expired` rows, from any surface, replace it with the outcome (`chat.update`). Layout (`src/slack/decision-message.ts`): a section with `*Permission needed*` or `*Question*`, the short id (first six hex digits of the decision id) and the tool title and command or the question; an actions block with numbered buttons (`action_id` `cm-decision:<n>`, `value` `<decision id>:<n>`); a context line with the text verbs and the deadline. Permission buttons: Allow once, one Always allow per rule the agent proposed (labelled with `_meta.rule`, else the option name), Deny. Question buttons: the choices of a single choice field (or Yes / No for a single boolean field), then Decline. Settled: the buttons are replaced by the outcome in the chat panel's wording, `Allowed once by @member in Slack`, `Denied in the web app` (with the reason), `Answered ...` (with the values), `Refused` (timeout, exit) or `Withdrawn` (turn ended).

Text verbs are thread replies, read after `slackTextToPlain`: `yes <id>` allows once; `no <id> [reason]` denies (the reason goes to the agent) or declines a question; `choose <id> <n>` (or `choose <n> <id>`) picks button `n`; `answer <id> <text>` answers a question, the whole text for one field or one `Title: value` line per field (choices match by value or label, a multi-choice field takes a comma list, free-text fields take anything). The router calls `interceptReply` for every reply before the per-thread queue (a decision blocks the turn that queue waits on); it consumes the reply only when the id is a decision of the thread's current session and the member passes the same roster checks as a reply, so `yes` on its own or an unknown id still goes to the agent. A consumed reply gets `white_check_mark`, or a thread message saying why it did nothing (already answered, expired, bad number). Button presses arrive as `interactive` `block_actions`; members outside the roster are ignored, and a press on a settled message re-renders the outcome. Answers call `platform.decisions.answer(id, { optionKind, optionId?, answer?, explanation?, surface: 'slack', actorId: 'slack:<member id>' })`, so the first answer from Slack or the panel wins.

Restarts: posted messages are recorded in `platform_meta` under `slack-decision:<decision id>` (`{ botId, channel, ts }`) until their outcome is shown. On start every recorded message is re-rendered from the decision's log; a decision left pending by a dead process reads as expired, so the message shows `Refused`. No migration.

## Daemon-hosted MCP tools

The agent sees a narrow tool; the daemon keeps the credentials and the scope. `src/agent-mcp/host.ts` (`startAgentMcpHost({ db, servers })`, `platform.agentMcp`) serves each `AgentMcpServerDefinition` (`{ name, appliesTo(session), tools: [{ name, description, inputSchema, annotations?, call(args, { session, signal }) }] }`) as stateless Streamable HTTP on `127.0.0.1:<random port>` at `/mcp/<server>/<sessionId>`: POST only, one JSON response per request (no SSE), a random bearer token per server and session per daemon boot, requests with an `Origin` header or a foreign `Host` refused, and `appliesTo` asked again on every request. Nothing is stored: `SessionManagerDeps.mcpServers(session)` (wired to `agentMcp.serversFor`) runs at every launch and resume and passes `StartSessionOptions.mcpServers` (`LaunchMcpServer { name, url, bearerToken, tools }`, checked by `assertLaunchMcpServers`: loopback http URL, names, token, tools) to the family launcher. Claude Code gets `--strict-mcp-config --mcp-config <inline JSON>` appended after the posture flags (never in the stored posture, where `--mcp-config` stays refused) and the tool's allow rule `mcp__<server>__<tool>` in the stored `--allowedTools`; Codex gets `CODEX_CONFIG.mcp_servers.<name> = { url, http_headers, enabled_tools, default_tools_approval_mode: 'approve' }`. Tool names live in `src/agent-mcp/tools.ts` (`WRAPPED_MCP_TOOLS`); `resolveBotPosture({ mcpTools })` takes only those, and `assertPostureNotWidened` refuses any other `mcp__` allow rule. A new wrapped tool: add it to `WRAPPED_MCP_TOOLS`, write its server definition, return it in `mcpServers` from the owning capability definition's `start` (the host serves every definition's servers and names none itself) and pass it in `mcpTools` where the bot session is started.

The one tool today is `post_blocks` on `candy_mountain_slack` (`src/slack/mcp.ts`, rule `mcp__candy_mountain_slack__post_blocks`): only sessions whose `posture.bot.holder.kind` is `slack` get it (plain and console sessions do not), and it is allowed in every write scope. The thread comes from the session's `slack_threads` row (open, same bot, holder id matching), never from the agent; `validateSlackBlocksPost` (`src/slack/block-kit.ts`) accepts only `text` (required fallback, at most 3,000 characters), `blocks` (1 to 50, at most 30,000 characters of JSON, types section, header, divider, context, actions, image, markdown, rich_text with their required fields) and optional `channel` / `thread_ts` that must equal the thread's; anything else (`reply_broadcast`, `username`, ...), another channel or thread, `<!channel>`/`<!here>`/`<!everyone>` or a broadcast element, `action_id`/`block_id` starting `cm-` (the daemon's decision buttons) and strings that look like Slack, GitHub, OpenAI/Anthropic or AWS credentials or private keys are refused with a reason the agent reads. Accepted posts go out as `chat.postMessage` with the bot's token. A persona whose front matter sets `tools:` must list the rule for the bot to see the tool. Not verified against logged-in CLIs here: whether plan mode (read-only scope) lets the allowed tool run.

## Slack handoffs

`src/slack/handoffs.ts` is the router's turn-end hook: the bots definition starts it as `startSlackHandoffs({ db, slack, botSessions, sessions }, BotsOptions.slackHandoffs)`, offers it as `BOT_SLACK_HANDOFFS` and runs its `onTurnEnd` before any `BotsOptions.slackRouter.onTurnEnd` passed in. A completed turn whose text holds a handoff block (`parseHandoff` from `@candy-mountain/shared`) has its message replaced by a card (`chat.update` with `blocks` and fallback `text`; a turn that posted nothing gets one `chat.postMessage`, claimed first in `platform_meta` under `slack-handoff:<turn id>`). Layout (`src/slack/handoff-message.ts`): the agent's text without the block as a `markdown` block, then the outcome and summary, the pull request (`#<number>` for GitHub and GitLab URLs) and issue short ids (`X8M.7.6`, as the issues list shows them), follow-ups, and a Mark done button (`action_id` `cm-handoff:done`, `value` the `slack_turns` id) with a confirm dialog. Without a block, or with a malformed one, the streamed message stays as it is: it already is the raw text. Cancelled turns stop there.

Every completed or failed turn appends one `bot.handoff` activity event: title `<bot name>: <summary>` (or the first line of the agent's last message), link the Slack permalink of the card (`chat.getPermalink`; the project's bots page when Slack does not answer), payload `{ turnId, botId, sessionId, slackThreadId, channel, threadTs, slackUrl, turnOutcome, outcome, summary, pullRequest, issueIds, followUps }`. The hook runs at least once, so the event is skipped when one with the same `payload.turnId` exists, and the card edit is the same each time.

Mark done does what a `done` reply does (`closeSlackThreadSession` in `src/slack/done.ts`, shared with the router): the thread closes, the session is closed and the worktree is released only when its work is on origin, and the same `Done. ...` reply is posted. The presser and the thread's opener must both pass `mayMemberTalkToBot`. The card is then rendered from the turn's log with `Marked done by @member` in place of the button; a press on a closed thread, a thread that moved to a new session, or a redelivered envelope only re-renders it as `The session is closed.`

## Platform settings

`GET`/`PUT /settings/platform` (admin only, mounted when `AppDeps.secrets` is passed) hold the LLM gateway and platform agent settings. Values live in the `platform_meta` table (`llm.gatewayBaseUrl`, `platformAgent.modelId`); the gateway key is a secret (`platform:llm-gateway` / `api-key`) and is only ever reported as `gatewayKeySet`. ## Notifications

`src/notifications/` sends a Slack message when something happens in a project. Rules are per project, one per kind (`NOTIFICATION_KINDS` in `@candy-mountain/shared`): `bot.finished` (from `bot.handoff`), `incident.opened`, `incident.closed`, `deploy.succeeded` and `deploy.failed` (both from `deploy.attempted`, told apart by `payload.outcome`, one of `DEPLOY_OUTCOMES`: `succeeded` | `failed`; any other outcome notifies nobody). A rule is `{ enabled, destination: { channelId } | { memberId } | null, lastFailureAt, lastFailureReason, lastDeliveredAt }`; an enabled rule must have a destination. Rules live in `platform_meta` as one JSON blob per project (`notifications.<projectId>`), no table of their own; a project's blob is not removed when the project is deleted (it is small and keyed by a uuid that is never reused).

`GET`/`PUT /projects/:slug/notifications` (admin only, `projectNotificationsPath(slug)`) -> `{ rules }`. `PUT { rules: { <kind>: { enabled?, destination? } } }` merges: kinds left out are unchanged, and a kind that is present has its last failure cleared. Errors: `invalid_request` 400 (unknown kind, bad id, enabled without destination, both ids), `forbidden` 403, `not_found` 404.

The dispatcher (`platform.notifications`, started by `startPlatform`) subscribes to `subscribeActivityEvents(db, listener)` in `src/activity/events.ts`, so it sees every `appendActivityEvent` on the platform database in-process; there is no polling and no catch-up after a restart. For each event with a matching enabled rule it builds one `NotificationDelivery` (workspace, kind, destination, title and `CM_WEB_URL` + the event's `link`, or the project page when the event has none) and offers it to the `NotificationChannel`s the capability definitions returned, in list order: a channel answers false when it has no identity for that workspace and throws for a failed delivery. The dispatcher knows nothing of Slack; the Slack channel (`src/slack/notifications.ts`, offered by the `slack` definition) posts the title (mrkdwn-escaped) and an `Open in Candy Mountain` link through the project's first bot (by name) that has a Slack bot token (`connections.web(botId)`), else the platform-level Slack plugin instance, else declines. When no channel accepts, or none is offered, the dispatcher records `lastFailureAt` / `lastFailureReason` (`No delivery channel: ...`) on the rule and carries on. A channel error is recorded the same way; a success stamps `lastDeliveredAt` and clears the failure. Each delivery has 10 s in total.

Exactly-once: delivered event ids are kept per project in `platform_meta` (`notifications.delivered.<projectId>`, the last 500 ids) and an id is claimed before anything is sent. The tradeoff is at-most-once: a crash between the claim and the post loses that message rather than repeating it, and an id older than the ring would be delivered again if it were ever re-emitted, which nothing does today.

Producers: a `bot.handoff` event should carry `link` to the thread (`/p/<slug>/agents/<threadId>`) so the message opens it; incident events should link to the monitor; `deploy.attempted` must set `payload.outcome` to `succeeded` or `failed`.

## Agent sessions (ACP harness)

`src/acp/` drives Claude Code and Codex over ACP with `@agentclientprotocol/sdk` 1.4.0 (`ClientSideConnection` over the child's stdio; 2.x removed that class, so the version is pinned here and in `packages/claude-acp`). The chat-claude-code definition (`chatClaudeCodeDefinition({ acp?, sessions?, decisions? })`, `src/chat-claude-code/definition.ts`) creates the harness (`createAcpHarness()`) and offers it as `ACP_HARNESS`; its close and the daemon's shutdown kill every live session (SIGTERM to the process group, SIGKILL after 5s).

`acpHarness.startSession({ family, cwd, configHome, env?, flags?, codex?, command?, upstreamSessionId?, onEvent?, turnTimeoutMs? })` spawns one process per session and completes `initialize` plus `session/new` (or `session/load` with `upstreamSessionId`) before resolving:

- `claude-code`: `node <@candy-mountain/claude-acp>/dist/cli.mjs --config-dir <configHome> [--claude <command>] [--turn-timeout-ms N] -- <flags>`; the shim sets `CLAUDE_CONFIG_DIR` and strips API-key variables itself. Needs `pnpm build` first.
- `codex`: `node <@agentclientprotocol/codex-acp>/dist/index.js` (pinned 2.3.0) with `CODEX_HOME=<configHome>`, `NO_BROWSER=1` (no browser login), `DEFAULT_AUTH_REQUEST=` and `APP_SERVER_LOGS=` (no auto-login, no transcript log files), `INITIAL_AGENT_MODE=<codex.mode>`, `CODEX_CONFIG={"developer_instructions": <codex.developerInstructions>, "model": <codex.model>, "model_reasoning_effort": <codex.reasoningEffort>}` plus `"sandbox_workspace_write": { "writable_roots": <codex.writableRoots> }` (only the keys that are set; empty when none is) and `CODEX_PATH=<command>` when given; the adapter runs the bundled `@openai/codex` otherwise. Posture is `codex: { mode?, developerInstructions?, model?, reasoningEffort?, writableRoots? }` (model and effort must be plain ids and writable roots absolute paths in `workspace-write` mode, or `AcpLaunchError`; `SessionManager.create` runs the same check as `invalid_request`): `mode` is `read-only` (default: on-request approvals reviewed by the user, read-only sandbox) or `workspace-write` (the same approvals over a workspace-write sandbox, no network); see `CODEX_MODE_POSTURE`. The adapter resends the mode's approval policy and sandbox with every turn, so the mode is the whole posture; that per-turn sandbox has no writable roots of its own, so `writableRoots` also go out as ACP `additionalDirectories` on `session/new` and `session/load`, which the adapter adds back to every turn. `AcpLaunchError` refuses, before anything is spawned: the auto-review mode `agent` (Codex approves its own escalations), `agent-full-access`, any other mode id (the adapter would fall back to auto-review), any `flags` (the adapter's only argv commands are `login`, which opens a browser, and `cli`, which bypasses ACP), and any `env` name in `CODEX_LAUNCHER_ENV` (`CODEX_HOME`, `CODEX_PATH`, `NO_BROWSER`, `INITIAL_AGENT_MODE`, `CODEX_CONFIG`, `DEFAULT_AUTH_REQUEST`, `APP_SERVER_LOGS`, `MODEL_PROVIDER`, `DISABLE_MCP_CONFIG_FILTERING`). `codex` options on `claude-code` are refused too. Never send ACP `authenticate`, `session/set_mode` or a `mode` config option to a Codex session: those are how a browser login or the auto-review mode would come back.

`configHome` is created `0700` (symlinks refused). The child environment is an allowlist (`AGENT_ENV_ALLOWLIST`: `PATH HOME LANG LC_ALL LC_CTYPE TERM TZ USER LOGNAME SHELL TMPDIR`) plus the family variables plus `env`; `env` names matching `AGENT_ENV_DENIED_NAMES` / `AGENT_ENV_DENIED_PREFIXES` (`ANTHROPIC_*`, `OPENAI_*`, `CODEX_API_KEY`, `CM_*`, `AWS_*`, OAuth refresh tokens, `NODE_OPTIONS`, ...) throw `AgentEnvError`. `CLAUDE_CODE_OAUTH_TOKEN` is allowed in `env`, which is how a pasted long-lived token reaches the CLI.

A missing login rejects `startSession` with `AcpAuthRequiredError` (ACP `-32000`); never probe `claude auth status` before a session. Other failures are `AcpStartError` with the child's stderr tail. The session handle has `prompt(text | ContentBlock[])` (resolves `{ stopReason, usage }` at turn end, one turn at a time), `cancel()`, `close()`, `subscribe(listener)` and `events()` (async iterable until exit), plus `id`, `upstreamSessionId` (what to pass back as `upstreamSessionId` to resume), `pid`, `status`.

Events are `AcpSessionEvent` (`src/acp/events.ts`): `{ seq, at, sessionId }` plus one of `text` (`role: 'agent' | 'user'`), `reasoning`, `tool_call`, `tool_result` (ACP `tool_call_update`), `usage`, `other` (any other session update, verbatim), `permission_request` and `question` (each with `requestId` and `respond()` returning `false` once the request can no longer be answered), `request_cancelled`, `turn_end`, `error` (`phase: 'prompt' | 'cancel' | 'connection'`), `auth_required`, `exited` (`expected` is true when the daemon closed it). Pending requests are answered with their cancelled outcome when the turn is cancelled (as ACP requires), ends, or the session closes; decisions should be chosen by option `kind`, never position.

Never-bypass: `resolveFamilyLaunch` runs `assertClaudeNeverBypass(flags)` on every Claude Code launch and throws `AcpBypassRefusedError` (an `AcpLaunchError`, `code: 'bypass_refused'`, `setting` names what was refused) before anything is spawned for `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode bypassPermissions` or `auto` (or any mode outside `CLAUDE_LAUNCH_PERMISSION_MODES`: `default plan acceptEdits manual dontAsk`), `--permission-prompt-tool` (prompts must reach the daemon), an `--allowedTools` / `--allowed-tools` rule that allows everything (`*`, a tool-name wildcard other than `mcp__<server>__*`, bare `Bash` or `Bash(*)`), a `--settings` / `--agents` value whose `defaultMode` / `permissionMode` is a bypass mode or whose `permissions.allow` holds such a rule (inline JSON or an absolute file; anything unreadable is refused), and the `bypassPermissions` / `dangerously-skip-permissions` tokens in any other flag (prompt text excepted). `sessions.create` applies the same check, so `POST /projects/:slug/sessions` answers 400 `invalid_request`. Codex is covered by its own launcher rules above.

Tests: `src/acp/test-support/fake-acp-agent.mjs` is a scripted stdio ACP agent; the Claude family is tested through the real shim (from source via tsx) driving `packages/claude-acp`'s fake `claude`. `src/acp/integration.test.ts` uses the real CLIs when present (`CM_TEST_CLAUDE_BIN` or `claude` on PATH; the Codex adapter is always installed) and only asserts `auth_required` on a fresh home unless `CM_TEST_CLAUDE_CONFIG_HOME` / `CM_TEST_CODEX_HOME` name logged-in homes.

## Durable agent sessions

`src/sessions/` puts a durable session on top of the harness: a row in `agent_sessions` (project cascade, `family`, `actor_id`, `cwd`, `upstream_session_id`, `status`, `posture` JSON, `created_at`, `last_activity_at`) and a per-session log in `agent_session_events` (`session_id`, `seq`, `kind`, `payload` JSON, `created_at`; primary key `(session_id, seq)`). `seq` starts at 1 and only grows, across resumes and daemon restarts; the log is the transcript the browser renders and replays. The chat-claude-code definition creates the manager (`createSessionManager(deps, settings)`) and binds it to two keys: `THREAD_SESSIONS` (`src/threads/sessions.ts`, the platform-owned narrow `ThreadSessions` the thread service reads through `runtime.service`) and `ACP_SESSIONS` (`src/chat-claude-code`, the full `SessionManager` for definitions that declare `dependsOn: ['chat-claude-code']`); the session routes are the definition's `workspaceRoutes`, so `createApp({ runtime })` mounts them on `/projects`. The definition also brings the `claude-code` plugin type and registers the `claude-code` session family (`sessionFamilies`); the chat-codex definition (`chatCodexDefinition()`, `src/chat-codex/`) declares `dependsOn: ['chat-claude-code']`, brings the `codex` plugin type and family the same way, and registers its launcher on `ACP_SESSIONS` at start. Each ACP family's launch lives with its definition as a `SessionLauncher` (`assertPosture` for `create`, `launch` for the harness options), registered with `sessions.registerLauncher(family, launcher)`; a family without one is `family_unavailable`. The bots definition (which also runs Slack routing) declares `dependsOn: ['chat-claude-code', 'chat-codex', 'slack']` (codex bots need the family and plugin type chat-codex brings) and reads `ACP_SESSIONS` and `ACP_DECISIONS` through `context.service`, so a list without any of those must leave bots out too, and boots with the bot routes answering not found. `platform.close()` is async: it stops the notification dispatcher and the MCP host, awaits the definitions (which may still write their last rows) and shuts the database last. Tests start one with `startAcpPlatform(dir, { acp?, sessions?, decisions?, worktrees?, slackRouter?, slackDecisions?, slackHandoffs?, slack?, ...platformOptions })` from `src/chat-claude-code/test-support.ts`, which also pulls `sessions`, `decisions`, `acpHarness` and `botSessions` out of the runtime. On boot every row's `status` is reset to `idle`; nothing is live until prompted.

Lifecycle: a session is created idle (`session.started` activity event). The first prompt resolves the family's launch context (`claudeCodeLaunchContext` / `codexLaunchContext`: the plugin's private home, CLI path and env; no login probe) and starts the live process, or `session/load`s the stored `upstream_session_id` on a later one, then sends the turn. `status` is `idle` (no process), `queued`, `starting`, `live` (process up, no turn) or `prompting`. The reaper kills a `live` process idle for `CM_SESSION_IDLE_TIMEOUT` (the row and its log stay; the next prompt resumes it) and `CM_SESSION_MAX_LIVE` caps live processes across all projects: a prompt beyond the cap is logged and queued FIFO, and the least recently active idle process is closed at once to make room. `platform.close()` and shutdown close every live process; the `exited` rows are written when the database is still open.

Routes (any authenticated actor; the actor id is recorded on create; `cwd` is the project checkout):

- `POST /projects/:slug/sessions` `{ family: 'claude-code' | 'codex', posture?: { flags?: string[], codex?: { mode?, developerInstructions? } } }` -> 201 `{ session }`
- `GET /projects/:slug/sessions` -> `{ sessions }` (oldest first); `GET /projects/:slug/sessions/:id` -> `{ session }`
- `POST /projects/:slug/sessions/:id/prompt` `{ text }` -> 202 `{ session }` once the turn is running or queued; the turn's events arrive on the stream
- `POST /projects/:slug/sessions/:id/cancel` -> `{ session }` (stops the running turn, or drops a queued prompt with a `turn_end` `cancelled`)
- `GET /projects/:slug/sessions/:id/events?after=<seq>` -> SSE: `: connected`, then every log row with `seq > after` as `event: session` / `id: <seq>` / `data: AgentSessionEvent`, then `event: status` `{ status }`, then live rows and status changes; `: ping` every 30 s. Reconnect with the last `seq` seen. The stream ends on shutdown.

Errors (`ApiErrorBody`): `invalid_request` 400, `not_found` 404 (project, or a session of another project), `session_busy` 409 (a turn is running or queued), `auth_required` 409 (the agent reported no login: the log also gets an `auth_required` row), `family_unavailable` 422 (no plugin instance for the family, or a Claude token mode without a token), `agent_failed` 502 (the process failed to start; an `error` row with `phase: 'start'`).

Log rows are `AgentSessionEvent` (`@candy-mountain/shared` `sessions.ts`): the harness kinds with `respond` stripped (`text`, `reasoning`, `tool_call`, `tool_result`, `usage`, `other`, `permission_request`, `question`, `request_cancelled`, `turn_end`, `error`, `auth_required`, `exited`) plus `prompt { text }` for what the user sent. History an agent replays on `session/load` is not re-logged.

Other callers: `sessions.create({ projectId, family, actorId, cwd, posture? })` for a worktree session, `sessions.prompt(id, text)`, `sessions.cancel(id)`, `sessions.subscribe(id, listener)` (`{ type: 'event', event } | { type: 'status', status }`), `sessions.observe(observer)` (every session, after its own listeners), `sessions.record(id, payload)` (a daemon-written row such as a decision), `sessions.events(id, { after })`. `pendingRequests` / `respondToPermission` / `respondToQuestion` are the raw hooks the decision service uses; answer through decisions instead.

## Pending decisions

`src/decisions/` turns every `permission_request` and `question` row into a decision (`Decision` in `@candy-mountain/shared` `decisions.ts`): `id`, `sessionId`, `requestId`, `kind` (`permission` | `question`), `toolCall` or `request`, `options` (`{ kind: allow_once | allow_always | deny | answer, optionId, label, meta }`; `meta` is the agent's own `_meta` for the option, e.g. the rule an always-allow saves), `createdAt`, `expiresAt`, `state` (`pending` | `answered` | `expired`), `answer` (`{ optionKind, optionId, answer, explanation, surface, actorId, at }`) and `expiry` (`{ reason: timeout | cancelled | exited | refused, message, at }`). The chat-claude-code definition creates the service (`createDecisionService({ db, sessions }, { timeoutMs?, now? })`) and offers it as `ACP_DECISIONS`, mounting the decision routes with the session routes; it keeps live sessions' decisions in memory and writes each change to the session log as `decision_opened { decision }`, `decision_answered { decisionId, answer }` and `decision_expired { decisionId, expiry }`, so they arrive on the SSE stream right after the request row and are rebuilt from the log after a restart (a decision the log left pending with no live request reads as expired).

Options: a permission's `allow_once` / `allow_always` / `reject_once` options become `allow_once` / `allow_always` / `deny`; `reject_always` and any option mentioning auto review are dropped; a deny with `optionId: null` (sent as the cancelled outcome) is added when the agent offered none. A permission with malformed or duplicate options, or a question that is not a form of string, number, integer, boolean or choice-list fields, is refused at once (`decision_expired` reason `refused`). A question offers `answer` and `deny` (decline).

`decisions.answer(decisionId, { optionKind, optionId?, answer?, explanation?, surface: 'web' | 'slack', actorId })`: chosen by kind, never position; `optionId` is required only when the decision has several options of that kind and must be one of them; `allow_always` only exists when the agent proposed a rule; `answer` (question only) must match the form (known fields, required ones present, choices respected unless the agent marked the field free text); `explanation` goes back with a permission deny. The first valid answer wins; a later one from any surface is `already_answered`. Past `expiresAt` (`CM_DECISION_TIMEOUT`, default 5m) the agent is refused (cancelled outcome / `cancel`) and the decision expires; a turn that ends or is cancelled expires it as `cancelled`, a process exit as `exited`.

Routes (any authenticated actor; the actor id is recorded; surface `web`):

- `GET /projects/:slug/sessions/:id/decisions` -> `{ decisions }` (oldest first)
- `POST /projects/:slug/sessions/:id/decisions/:decisionId` `{ optionKind, optionId?, answer?, explanation? }` -> `{ decision }`; any other field is refused

Errors (`ApiErrorBody`, `DECISION_ERROR_CODES`): `invalid_request` 400 (bad body, unknown kind, ambiguous kind without `optionId`), `not_found` 404 (session or decision), `already_answered` 409, `decision_expired` 409, `option_not_offered` 422 (kind or `optionId` the decision does not offer, including `allow_always` with no proposed rule), `invalid_answer` 422.

## Chat threads

Chat agents come from the `chat-claude-code` and `chat-codex` capabilities (Agent Hub module, default rung `chat`; ladder `none` -> `chat` with chat on; no views). Each contributes one agent: `claude-code` (family `claude-code`, avatar `i-lucide-sparkles`, requires the `claude-code` plugin) and `codex` (family `codex`, avatar `i-lucide-square-terminal`, requires `codex`). An agent manifest's optional `family` and `avatar` show up on `RegistryAgent`; the registry lists an agent only when its capability is ready and the actor's rung allows chat.

`src/threads/` keeps `chat_threads` (project cascade, `actor_id`, `agent_id`, `current_session_id` -> `agent_sessions` cascade, `title`, `model`, `effort`, `unread`, `working`, `last_read_at`, `last_activity_at`, timestamps) and `chat_thread_sessions` (every session a thread has wrapped, with its model and effort). A thread is per actor, project and agent and wraps one session at a time, created with `sessions.create` on the project checkout (`sourcePath(project.source)`); changing the model or effort starts a new session on the same thread. `working` follows the current session's status (`queued`, `starting`, `prompting`) through a session subscription, including prompts sent on the session routes; a turn that ends sets `unread` until the thread is marked read. Prompting or cancelling through the thread marks it read for the sender. On boot `working` is recomputed from the (reset) session statuses.

Routes, all under `/projects/:slug/threads` and gated by the chat rung of the agent's capability (`requireCapability({ capability, chat: true })`); another actor's thread is a 404:

- `GET ?agent=<id>` -> `{ threads }` most recently active first; without `agent` it covers every agent the actor may chat with and is refused only when none is allowed
- `POST` `{ agentId, title?, model?, effort? }` -> 201 `{ thread, session, sessions }`
- `GET /:id` -> `{ thread, session, sessions }`; `PATCH /:id` `{ title?, model?, effort? }` -> same (a model or effort change mid-turn is `thread_busy` 409)
- `POST /:id/read` -> `{ thread }`; `POST /:id/prompt` `{ text }` -> 202 `{ thread, session }`; `POST /:id/cancel` -> `{ thread, session }`
- `GET /agents/:agentId/options` -> `{ options: { agentId, family, models, efforts } }`; empty lists mean no selector

Stream a thread with the session events route on its `currentSessionId`. Model and effort: Claude Code offers the CLI aliases `opus`, `sonnet`, `haiku` (a full `claude-*` id is accepted too), passed as `--model`, and effort `low`/`medium`/`high`, passed as `--settings {"effortLevel":...}`. Codex offers what its adapter reported: `AcpSession.configOptions` holds the `configOptions` of `session/new`/`session/load` (and later `config_option_update`s), the session manager keeps them per project and family in memory, one set per model the agent ran with (`SessionManager.configOptions`), and the options route returns the latest `model` list plus every `reasoning_effort` seen. Before a Codex session has started in this project since boot both lists are empty, so the selectors stay hidden. A choice is checked against those lists (an effort a known model does not list is refused; a value the thread already has stays accepted after a restart empties them) and launches a new session with posture `codex: { model, reasoningEffort }`, which the launcher passes as `CODEX_CONFIG` `model`/`model_reasoning_effort`; nothing calls `session/set_config_option`. Errors add `unsupported_agent` 422 and `thread_busy` 409 to the session codes and the gate's `not_enabled`/`not_granted`/`not_ready`.
A family may run in-process instead of through the harness: `ThreadService.prompt(thread, text, actor)` looks the session's family up in `ThreadServiceOptions.native` (the `chatFamilies` of every started definition, each checked at boot against the registered session families; a `NativeFamilyRunner` per family) and, when one is registered, calls `sessions.run(sessionId, text, runner)`, which logs the prompt, sets the status to `prompting`, lets the runner append rows through `emit`, then appends `turn_end` (`end_turn`, `cancelled` after a cancel, `error` when the runner threw, with an `error` row first) and returns the status to `idle`. Cancel aborts the runner's `signal`. Everything else (working and unread, SSE, the chat panel) is unchanged because the rows and status changes are the same ones a harness session produces. A family without a runner that no harness launches (`platform` on the plain session routes) is `family_unavailable` 422.

Bots as chat agents: the registry adds one agent per project bot that is usable from the console, `{ id: 'bot:<bot id>', capabilityId: 'bots', label: <bot name>, family, avatar: 'i-lucide-bot', kind: 'bot', bot: { id, writeScope, baseBranch } }`. Usable means `computeBotStatus` would be `active` with both Slack keys set (`botUsableWithoutSlack`, read synchronously by `listProjectBotRefs`; a blank base branch is not resolved here and fails at start with `repository_not_configured` if the host cannot be read). The actor needs chat on `bots` (its `manage` rung allows chat; the manifest sets `projectAgents: true` so a chat rung needs no declared agent) and on the bot family's chat capability (`chat-claude-code` / `chat-codex`), because the session stream and decisions are gated on that one; the thread routes check both. `POST /threads { agentId: 'bot:<id>' }` calls `botSessions.start` with the new thread as console holder (worktree, persona, posture) instead of a checkout session; model and effort are refused (400) and the options route returns empty lists. A bot thread's prompt goes through `botSessions.prompt` (lease touch); if its worktree was released it starts a fresh session and worktree on the same thread first. `POST /threads/:id/close` (bot threads only, else `unsupported_agent`) calls `botSessions.closeSession` -> `{ thread, session, sessions, bot, released, keptUnpushed }`. Every bot thread response carries `bot: { botId, name, worktreePath, branch, baseBranch, worktree: 'active' | 'released' | 'none', keptUnpushed, unpushedReason }`.

## Platform agent

The `platform-agent` capability (`src/platform-agent/manifest.ts`) is standalone (in no module, so a candidate for every project), has no views, requires the `llmGateway` platform fact, grants `chat` to everyone through `everyoneRung`, and contributes the registry agent `platform` (family `platform`, avatar `i-lucide-mountain`) with three tools on the `chat` rung: `open_view`, `start_chat`, `describe_platform`. Until the gateway base URL, key and model id are all set on the Settings page the capability is not ready, so the agent is absent from `registry.agents` (the rail hides it), the admin sees the `platform-fact` reason, and creating or prompting one of its threads is refused `not_ready` 409.

`src/platform-agent/` holds the agent. `createPlatformAgent({ storage })` builds one Mastra `Agent` registered in `createMastra` under the id `platform`; its instructions, model and tools are dynamic arguments resolved per turn from the Mastra request context (`PlatformTurnContext` under `PLATFORM_TURN_KEY`): the actor, the project, the actor's `RegistryResponse` for that project (which is what the instructions and `describe_platform` are built from), a memoised `access(capabilityId)` -> `CapabilityAccess`, and the gateway settings. The model is an OpenAI-compatible config `{ providerId: 'llm-gateway', modelId, url: baseUrl, apiKey, api: 'chat' }`, so the gateway must speak `POST <baseUrl>/chat/completions`. Memory is `@mastra/memory` on the same LibSQL store (last 30 messages, no title generation, no semantic recall): the memory thread id is the chat thread id and the resource is the actor id, so a thread continues across turns and an actor's threads stay theirs.

`createPlatformAgentRunner(deps)` (`RegistryDeps` plus `secretsReader: SecretsStore` and `mastra`) is the `NativeFamilyRunner` for the `platform` family. Each turn it reads `resolveLlmGatewayConfig` (an `error` row with phase `start` if anything is missing), loads the registry, streams `agent.stream(text, { requestContext, memory, abortSignal, maxSteps: 6 })` and writes the log: streamed text as `text` rows (sliced no more often than every 150 ms), each tool call as `tool_call` (ACP-shaped: `toolCallId`, `title`, `kind: 'other'`, `status: 'in_progress'`, `rawInput`) and `tool_result` (`status`, `rawOutput`, a one-line text `content`), and, when a tool answered with an action, a `client_action` row `{ toolCallId, action }`. The transcript renders tool rows as it does for any agent and ignores `client_action` until the chat layer applies it.

Tools return values, never throw: `PlatformToolRefusal` `{ refused: true, code, reason }` (a gate code, `not_found` or `invalid_request`) which the agent relays in words, or an action. Every tool first checks the actor's own rung on `platform-agent` (`checkTool`), then the target: `open_view({ viewId })` finds the manifest that owns the view and runs `checkView` on the actor's access to that capability, answering `{ kind: 'navigate', to, projectSlug, viewId, capabilityId }` (`to` is the registry's web route); `start_chat({ agentId })` finds the agent's capability and runs `checkChat`, answering `{ kind: 'open_thread', agentId, threadId? }` (the browser creates the thread; chatting with the platform agent itself is `invalid_request`); `describe_platform()` answers the actor's registry as `PlatformDescription`. Shared types are in `@candy-mountain/shared` `platform-agent.ts` (`PlatformClientAction`, `PlatformToolRefusal`, `PlatformActionResult`, `PlatformDescription`, `PLATFORM_AGENT_ID`, `PLATFORM_AGENT_TOOL_IDS`).

Tests (`src/platform-agent/platform-agent.test.ts`) use `startStubGateway(scriptedReply)` from `test-support.ts`, a tiny OpenAI-compatible server that picks a tool from the prompt's wording (`open <viewId>`, `chat with <agentId>`, `describe ...`) and answers from the tool result; `PUT /settings/platform` points the base URL at it. The same module serves a local live check.
## Worktrees

`src/worktrees/` keeps bots out of the checkout Jack edits: the project's path (`sourcePath(project.source)`) is the clone, and every bot session works in its own git worktree under `<data dir>/worktrees/<project id>/<lease id>` on its own branch. Leases are rows in `worktree_leases` (`id`, `project_id` cascade, `holder_kind` `session` | `bot`, `holder_id`, `path`, `branch`, `base_branch`, `state` `active` | `released`, `created_at`, `updated_at`, `last_used_at`, `released_at`, `unpushed_work`, `unpushed_reason`, `inspected_at`, plus `dependencies_status` / `dependencies_output` / `dependencies_checked_at` for dependency installs; one active lease per holder). The bots definition creates the pool (`createWorktreePool({ db, paths, git?, now? }, { maxPerProject? })`, options from `capabilityDefinitions({ bots: { worktrees } })`) and offers it as `BOT_WORKTREES`; the cap comes from `CM_WORKTREES_PER_PROJECT`. There are no HTTP routes.

- `worktrees.acquire({ projectId, holder, baseBranch, branchName?, installDependencies? })` -> `WorktreeLease`. Fetches the base from the clone's remote (`origin`, else its first remote) and cuts the branch from `<remote>/<base>`, or from the local base branch when the clone has no remote; `--no-track`, so the agent publishes with `git push -u origin <branch>`. `branchName` defaults to `cm/<holder kind>/<holder id>`; bots pass `botBranchName(botName, sessionId)` = `cm/bot/<bot slug>/<session id>` so the branch names both.
- `worktrees.resume(holder, { installDependencies? })` -> the holder's active lease with the same `path` (touches `last_used_at`), or `null`. A vanished directory is added back on the lease branch (its commits survive; uncommitted work does not), or cut from the base again if the branch is gone too.
- `worktrees.release(leaseId, { force? })` removes the worktree directory and its registration, keeps the branch, and marks the lease `released` (idempotent), but only when the worktree is safe to remove (below). Otherwise the lease stays `active` and is returned with `unpushedWork: true` and `unpushedReason` (e.g. `1 uncommitted change(s), 2 commit(s) not on origin`); the idle reclaim retries it later. `force: true` skips the check and is only for an explicit human decision to discard the work.
- `worktrees.list(projectId, { includeReleased? })`, `worktrees.get(leaseId)`.
- `worktrees.withProjectLock(projectId, fn)` serialises every git command on a clone and its worktrees; `acquire`/`resume`/`release` run inside it, and so must any other git operation on the project (reclaim checks, dependency installs). `worktrees.git(cwd, args, { timeoutMs? })` is the runner: `git` spawned without a shell, `GIT_TERMINAL_PROMPT=0`, killed with its process group on timeout, `GitError` with `stderr` and `exitCode`.

Dependencies: after the worktree is created (and when `resume` adds a vanished one back), `acquire` installs its dependencies unless `installDependencies: false`, outside the project lock, and records the outcome on the lease as `lease.dependencies` = `{ status: 'installed' | 'skipped' | 'failed', output, checkedAt }` (`null` when no install was attempted); `worktrees.installDependencies(leaseId, { timeoutMs? })` runs it again. A failed install never fails the acquire. Detection (`detectPackageManager(dir)` in `install.ts`) reads the worktree root: no `package.json` or no lockfile -> `skipped`; `pnpm-lock.yaml` -> pnpm, `package-lock.json` / `npm-shrinkwrap.json` -> npm, `yarn.lock` -> yarn; with several lockfiles the `packageManager` field picks among them, else pnpm, then yarn, then npm. Commands, run with the binary on the daemon's PATH: pnpm `install --offline --frozen-lockfile`, then `install --frozen-lockfile --prefer-offline` if that fails; npm `ci --prefer-offline --no-audit --no-fund`; yarn `install --immutable` for a Berry lockfile (`__metadata:`), else `install --frozen-lockfile --prefer-offline --non-interactive`. One deadline covers all attempts (`dependencyInstallTimeoutMs` pool option, default 5 minutes), after which the process group is killed. The environment is the agent allowlist plus XDG/pnpm/corepack/CA/proxy variables, never tokens. `output` is the last 4 KB of the combined output (the skip reason when skipped). `dependencyInstallState(lease.dependencies)` gives the `true | false | 'failed'` the bot's surface instructions take.

Holder: a bot session uses `{ kind: 'session', id: <agent session id> }`, since a session's `cwd` is fixed when it is created and resuming it needs the same directory. Errors (`WorktreeError`, `code`/`status`): `invalid_request` 400 (bad branch name), `not_found` 404 (project or lease), `lease_exists` / `branch_exists` / `cap_reached` 409, `base_branch_refused` (target equals base) / `base_branch_not_found` / `clone_unavailable` 422, `fetch_failed` 502, `git_failed` 500. Deleting a project cascades its lease rows; the directories under `worktrees/<project id>` stay for the orphan sweep.

### Reclaim and reconcile

`inspectWorktree(git, path, { fetch? })` decides whether a worktree directory is safe to remove: no `git status --porcelain` output (untracked files count; ignored files such as `node_modules` do not) and no commits on `HEAD` that are missing from every ref of the remote (`origin`, else the first remote), checked after a `git fetch` of that remote (a failed fetch falls back to the last known remote refs). A branch pushed under any name, or merged into a remote branch, counts as pushed; with no remote, commits must be on another local branch. A missing directory is safe; a directory git cannot read (e.g. its clone was deleted) is not.

The bots definition starts the reclaimer (`startWorktreeReclaimer({ db, paths, pool, now?, log? }, { idleTimeoutMs?, reclaimIntervalMs?, reconcileOnStart? })`, offered as `BOT_WORKTREE_RECLAIMER`) and its close stops it.

- `reclaimIdle({ idleForMs? })` runs every `CM_WORKTREE_RECLAIM_INTERVAL` and calls `release` on each active lease whose `last_used_at` is older than `CM_WORKTREE_IDLE_TIMEOUT`, so idle clean worktrees go and idle ones holding work stay flagged (logged once when first flagged). `last_used_at` only moves on `acquire`/`resume`, so a holder that works for longer than the timeout should `resume` again to stay fresh; a clean worktree is otherwise removed even while a session sits in it.
- `reconcile()` runs once at startup (`ready` settles with its report) without blocking the server: active leases whose directory is gone are released; directories under `worktrees/` with no active lease (including those of deleted projects) are removed when empty or safe and reported with a warning when not (`dirty`); empty project directories are removed; `git worktree prune` runs in every project's clone. Everything runs under the project lock.

bd from a worktree: `beadsEnvForWorktree(projectPath)` -> `{ beadsDir, env: { BEADS_DIR, BD_NON_INTERACTIVE: '1' } }`, or `null` when the checkout has no `.beads` (then the bot is told bd is not connected). Pass `env` as the session's `startSession({ env })` extras; they are not on the inherited allowlist, so a `BEADS_DIR` in the daemon's own environment never reaches an agent. bd 1.2.2 already finds the main checkout's `.beads` from a worktree through the git common directory, but `BEADS_DIR` (the `.beads` directory itself, not the repo root) wins over discovery, so bd still hits the main database from a subdirectory, a scratch directory outside the worktree, or a branch whose committed `.beads` holds only config. Writes go straight into the main checkout: no database or `issues.jsonl` appears in the worktree, config comes from the main `.beads/config.yaml` (the branch's copy is ignored), and with `export.auto` on the JSONL export lands in the main checkout, showing as a change in its `git status`. `bd init` inside the worktree refuses because the database exists. Limits: the bot's bd calls and the daemon's own runner share one embedded Dolt store and queue on its lock (eight concurrent creates from both sides all succeed in about 2.5s), so a long-held lock delays the Issues page; `BEADS_DIR` also wins in any other repo the bot `cd`s into; a sandbox that confines writes to the worktree (Codex `workspace-write`, Claude's Bash sandbox) blocks bd writes unless `beadsDir` is added as a writable root.
