# Phase 1: the platform treats an installed capability like a local one

Repository: `crab-shack/platform`. Depends on phase 0's fast lane, so each piece is released by the push that lands it.

## Installed capabilities are checked

Today the platform's package checks find capabilities by walking the product's workspace. A capability that arrives as a dependency is invisible to them: nothing confirms that it is listed in the daemon's definitions, that its declared dependencies match what its definition depends on, that it follows the capability and connection rule, or that it states the SDK major. The lint that polices import directions between capabilities has the same blind spot, and several checks assume every capability shares the product's scope.

Make every check a product runs over its capabilities cover installed capability packages as well as workspace ones, under any scope, with the same messages. A product that mixes its own capabilities with installed ones gets one answer covering both. A product generated by `platform-new product` gets these checks without editing anything.

Existing products with only workspace capabilities see no change.

## Linking to a capabilities checkout

`platform-link` lets a product try an unreleased platform change from a local checkout, and the guard stops a linked state being committed. It knows only the five platform packages. Capability work needs the same loop: change a capability in the local checkout and see it in a product at once, with no release in between. This is what keeps the publish step out of moment-to-moment work.

Extend linking so a product can link to a local capabilities checkout, on its own or together with a platform checkout, with the same guarantees: one copy of every shared library, nothing but the product's lock and workspace file touched, a clean unlink, and the guard catching a link left in place. Only the capabilities the product already depends on are linked.

## Documents

The capability author's pages say a capability is a package in a product's repository under the product's scope. Say the second shape too: a capability installed from the registry, how a product lists it, and how the checks treat it.

## Human test

In a product generated by `platform-new product`, install one capability from a packed tarball rather than the workspace. Leave it out of the daemon's definitions and confirm the product's tests name it. Add it and confirm they pass and the app shows it. Then link the product to the checkout the tarball came from, change a label there, see it in the running product, unlink, and confirm `git status` is clean.
