# Phase 3: capabilities are published, with the fast lane

Repository: `crab-shack/capabilities`. Depends on phase 2.

## Publishable packages

Each capability, each connection, the ACP shim and the test support is published to the organisation's private registry under its own version. An installed package works in a product the way the workspace package does: its daemon half runs under plain Node in a built daemon, its web layer is found and extended by the product's web app, and its migrations are found on disk and applied. Its test support stays out of its main entry, as now.

A capability that needs another declares it so that a product ends up with one copy of each, and so that installing a capability without what it needs fails at install or at boot with a message naming what is missing, never silently.

Every published package states the SDK major it targets, and the repository's README says which platform versions the current packages work with.

A product's CI must be able to read the new packages. The platform's registry access page covers how; extend it or point to it rather than writing a second one.

## The fast lane

Jack's blocker with the platform repository is the release loop: wait for the gates, open and merge a pull request, then merge a second, generated pull request to publish. During active development of the capabilities that loop is pure delay, and it is worse for an agent, which cannot merge its way through it.

Phase 0 gives the platform repository a fast lane. This repository gets the same one, built the same way, so there is one release habit across both. While it is on:

- **A push to `main` is the release.** Work is committed straight to `main`. There is no pull request to open and no generated release pull request to merge. Anything that changes a package says, in the same push, which packages change and by how much, and those versions are published without a further human step.
- **Publishing does not wait for the checks.** Lint, typecheck and tests still run on every push and report red or green, because knowing is free. They run beside the publish, not before it. The only thing that stops a publish is a package that does not build.
- **Nobody has to pull a robot's commit before pushing again.** If the release writes versions or changelogs back to `main`, the next push collides with it and the delay returns in a different form. Prefer a flow where the pushed commit already holds the versions.
- **An agent can release.** The repository's agent instructions give agents standing permission to commit and push to `main` when a piece of work is finished, which under this lane is the release. This is a deliberate exception to the conservative git rule Candy Mountain's instructions set, and it applies to this repository only.
- **Publishing from a laptop is the fallback**, for when the workflow itself is broken. Document what it needs.

What keeps this safe enough: products pin exact versions, so a bad release reaches a product only when someone moves that product to it; and most day-to-day work never publishes at all, because a product links to the local checkout (phase 1).

## Turning the gate back on

One documented switch restores the careful flow: the checks gate the publish, and changes arrive by pull request. Flipping it needs no rewrite of the workflows. The README says where the switch is, what each position does, and that the repository starts with it off. Note for whoever flips it: enforcing pull requests on a private repository needs a paid GitHub plan, which the organisation does not have today, so until then that half is a convention.

## Human test

Change a label in one capability, state the version bump and push to `main`. Without opening anything on GitHub, see the new version on the organisation's packages page within a few minutes, and see that no other package's version moved. Break a test on purpose and push: the checks run red and the publish still happens. Flip the switch, push the same kind of change with a red test, and confirm nothing is published. Flip it back. Finally, in a scratch product generated by `platform-new product`, install two capabilities where one needs the other, build the product and start its built daemon and web app.
