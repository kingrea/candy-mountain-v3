# Phase 3: Compatibility contract and scaffold

**Capability:** A capability built against the wrong SDK major is refused at boot with a clear message, and a new capability or a new product starts from a scaffold rather than a blank directory.

## What and why

**The compatibility check.** Each capability package declares the SDK major it targets as a peer dependency and carries that version in its definition. The daemon compares every definition's declared SDK against the SDK it is running and refuses to start when the majors differ, naming the package, its SDK and the platform's. The web side gets the same check at build time through the layer list, so a mismatched layer fails the build rather than the browser. The base's changelog states, for every major, what a capability author must change.

**The scaffold.** The template capability from the extraction plan becomes a generator in the base: a command that creates a new capability package in the current workspace with the chosen id and label, both entry points, a passing test and the README, styled only through the scoped forms the conventions document allows (`.ai-docs/plans/product-theme/`). A second generator creates a new product distribution: a repo skeleton with the two thin apps, product configuration with every theme field and an empty product stylesheet, the pipeline, registry authentication and one capability from the first generator. These are the two things a client engagement starts from, and the second is what the digital hub and the home dashboard are created with.

**Connection packages.** The capability generator offers both shapes the connection-packages plan (`.ai-docs/plans/connection-packages/overview.md`) defines: a feature capability (`cap-<id>`, with a manifest, bringing no plugin types) and a connection package (`plugin-<id>`, service-only, whose id is the plugin type it brings and which declares that type). A connection package is a capability definition under the same contract, so the compatibility check applies to it the same way: it declares the SDK major it targets, and the daemon refuses it at boot, naming the package, on a mismatch.

**Declared settings and the product file.** A capability's product-level settings today are a mix of factory options typed in TypeScript and environment variables each capability reads for itself, so a product that wants a capability tuned a certain way has to write code, and a teammate who wants to reuse that tuning has to copy the code. Each capability definition instead declares a settings schema, and the daemon validates every capability's settings against it at boot, naming the capability and the key when a value is wrong, the same way module definitions are validated against the capability registry. With settings declared as data, a product distribution can be described by one file (YAML or similar) that carries what the product configuration and module list carry today plus a settings block per capability, so a product with no code of its own is the two thin apps and that file. Factory options that are code, such as test fakes and callbacks, stay a TypeScript seam and are not part of the declared schema. Environment variables remain the override for secrets and machine-specific values like ports and the data directory, which the platform config already resolves. The product generator emits the file rather than a TypeScript product package, and the capability generator emits an empty settings schema. Settings are per product, not per module: a capability has one instance per daemon and a module only groups capabilities, so two modules in one product cannot carry different settings for the same capability. Revisit that only when a product needs it. The settings schema on the definition contract can land in the Candy Mountain repo ahead of the base repository; the file reader and generator belong here.

**Conventions as the contract.** The daemon and web conventions documents move into the base's documentation along with the capability author's guide. They state the directions a capability may import, the contribution points it may use, what the platform promises to keep stable across minors, and what it does not.

## Human test

Generate a capability into Candy Mountain, add it to both apps and see it running. Change its declared SDK major and confirm the daemon refuses to start naming it, and the web build fails naming it. Generate a product distribution into an empty directory, add one generated capability, run its pipeline and start it with the placeholder name and the capability's page showing. Put a wrong value for one of its settings in the product file and confirm the daemon refuses to start naming the capability and the key; put a right value and confirm the capability sees it.
