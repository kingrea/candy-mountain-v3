01

One product. A reusable platform.
Selected capabilities.

Candy Mountain is the assembled product. Its configuration chooses what exists; thin applications wire the chosen code into the daemon and web shell.

Product = choices

packages/candy-mountain lists capability, module, plugin-type and web-layer IDs, branding and scope language. The platform calls it a workspace; Candy Mountain calls it a project.

Platform = shared mechanics

The daemon owns auth, grants, workspaces, plugin-instance storage, registries and threads. The web shell owns layout, navigation, setup screens and generic chat.

Apps = assembly

apps/daemon supplies definitions; apps/web composes Nuxt layers. apps/cli supplies paths and product settings to the reusable process-management CLI.

Machinery other code uses

A service-only cap-* package shares runtime behaviour without a catalog feature or connection type. ACP is the agent-process runtime.

Platform-owned threads also uses a service-only definition.
“Service-only” does not mean “no UI”. A connection can contribute a login panel, icon or setup form. It has no feature manifest, so it gets no feature catalog entry, module membership or permission ladder of its own. Its routes still need authorization.

Target enforcement: a definition with a manifest cannot declare plugin types; a plugin-* definition must have no manifest and bring at least one plugin type; a cap-* definition brings none. The connection’s definition ID matches the type it brings, for example plugin-codex → codex. Epic task 02z.7 adds boot/lint enforcement.

Plugin type ≠ plugin instance

The type is code: “how Codex is configured and checked”. An instance is stored configuration. A workspace resolves its own instance first, otherwise the global one. An unhealthy local instance does not silently fall back to a global instance.

Module ≠ package ≠ layer

A module groups feature capabilities for workspace enablement and role grants. A package distributes code. A web layer contributes UI at build time. None of these terms implies a separate running service.

Fields are optional except the definition ID. “Types · families · facts” abbreviates plugin types, session families and workspace facts. Definitions can also declare activity event types and notification kinds.

Manifest: what access means

Declares views, agents, jobs and tools/operations. A ladder adds rights cumulatively: Issues uses none → read → write; Codex chat uses none → chat.

Context: what it receives

Database, paths, secrets, registries and product scope. context.service(KEY) resolves services only from direct declared dependencies. Service access is not transitive.

Layer: what the browser gets

Pages, components and contributions to shell slots: icons, forms, login panels, project cards and chat controls. A manifest describes a view; a layer implements it.

04

What 02z actually changes.

The shared agent runtime moves below the connections. Features can reuse a connection without importing another feature just to get its implementation.

Connections own the engine wiring

plugin-claude-code and plugin-codex own their plugin type, session family, launcher and connection UI. Both register launchers on ACP. Chat features retain their manifest and chat controls.

ACP owns shared execution

cap-acp owns harness, sessions, decisions and their routes, using the platform session store and repository path service. Bots consume the runtime and connections too, alongside their worktree, team and Slack responsibilities.

The same split applies to hosting

Deployments→HerokuNetlify

Provider clients and operations move into connection packages. Deployments keeps environments and live-version logic. Package dependencies on both providers do not mean every workspace must configure both.

Two connections get clearer names

Repository and Slack packages take the plugin- prefix. Their definition IDs stay repository and slack. Existing plugin-type IDs, routes, tables and stored instances stay stable. Newly extracted definitions are added to product composition.

This changes ownership, not behaviour. No new extension contract or product-file section. Bot chat currently requires access to both Bots and the family’s chat capability; session routes retain their gates. Moving the runtime does not remove those permission relationships.

Three different dependencies

dependsOn controls startup and service access. requiresPlugins checks healthy configured instances. requiresWorkspaceFacts checks facts such as hasBeads. One does not replace the others.

Readiness is more than “installed”

Missing secrets, no stored test result or a failed result block readiness. requiresAnyPlugins allows alternatives: Bots needs a healthy repository connection plus at least one of Claude Code or Codex.

The registry shapes navigation and available agents per workspace and actor. Admins can see degraded navigation to fix setup; ordinary users’ navigation hides unready features. Daemon handlers apply gates, while some setup and data routes use separate auth/admin checks. A manifest does not automatically protect every route.

06

From assembly to a running agent.

Definitions run together inside the daemon. Their contributions become routes, services, notifications and agent integrations.

Boot sequence · existing mechanism
Validate product→Build registries→Migrate data→Start definitions→Wire hosts + routes

Dependencies start first; shutdown and workspace-deletion hooks run in reverse order. start() returns synchronously, although runtimes can initiate asynchronous work. All selected definitions start at boot; workspace module switches do not load or unload their code.

Platform data

Workspaces, auth, grants, module enablement, plugin instances, activity and thread/session records.

Owned feature data

Repositories, bots, worktree leases, team members, issue assignees, uptime records and environments have owning schema/migration sets in the same application database.

Outside that database

Secrets have a separate store. Code lives in repositories and worktrees; issue records are accessed through bd and Beads. Provider state remains in the connected service.

Other paths use the same composition mechanism. Slack connections feed bot routing; uptime runtimes schedule checks; activity can trigger notification channels. The platform agent uses an in-process native runner and the configured LLM gateway, rather than the ACP coding-agent path.

The boundaries to check
against your mental model.

These are the consequences of the existing contract and agreed 02z split.

BoundaryWhat the architecture saysWhat follows
CompositionProduct lists and app dependencies explicitly select code.Build/boot composition. No runtime marketplace or hot-install mechanism is described here.
OwnershipTarget: connections own plugin types; features consume them.Features reuse one Codex type instead of defining duplicates. Product assembly still has to match.
Backend dependenciesPublic-entry imports, with package dependencies and dependsOn in agreement.Dependencies point toward the platform. Platform code does not import product packages; service access requires a direct declaration.
FrontendLayers compose through shell/chat contribution points.A backend dependency does not authorize importing another capability’s UI internals.
IsolationDefinitions share a process and receive database access.Code ownership is not a process or database security sandbox. ACP agents run in separate processes with their own execution policy.
PermissionsManifests define access; handlers apply it.Extracting ACP does not erase family-chat gates or bot eligibility rules.
Epic scopeMove existing connection/runtime code; enforce the ownership convention.Publishing, richer capability settings and product-file redesign are separate work. Existing behaviour should remain stable.
