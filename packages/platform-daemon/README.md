# @candy-mountain/platform-daemon

This is the conventions document for a capability's daemon half and the platform it plugs into. It is written for someone writing a capability; the `cm-packages` lint's rule docs point here. The web half has its own conventions document, `packages/platform-web/README.md`, and this one does not repeat it.

The platform is this package plus `@candy-mountain/platform-sdk`. This package is the daemon: the data directory, the database and the migration sets, secrets, auth, workspaces and organisations, the capability, module, plugin type and session family registries, plugin instances, grants, readiness and the registry answer, activity, notifications, threads, the agent MCP host, the app factory (`createApp`), platform start (`startPlatform`) and `runDaemon`. Production code reaches it through its root entry, and it knows no product. The SDK holds the contract a capability is written against: wire types and the product configuration on its root entry (no Node or DOM types), and the define helpers and contract types on its `./daemon` entry (`packages/platform-sdk/src/daemon/`, every field commented there). A capability is one package that hands the platform a **runtime definition**; a distribution (Candy Mountain's is `apps/daemon`) lists the definitions it runs and starts the platform. How Candy Mountain lists a capability is in `apps/daemon/README.md` ("Adding or removing a capability"). `packages/cap-template` is a complete capability that uses each part of this contract once; its README is the guide to copying it.

## Capability packages

There are three kinds, all held to the same contract and the same boundaries:

- **Feature capability**, `packages/cap-<id>`: a definition with a manifest, so it has views, tools, agents and a rung ladder, appears in the catalog, sits in modules and is granted (`cap-issues`, `cap-uptime`, `cap-bots`).
- **Service-only capability**, `packages/cap-<id>`: a definition with no manifest that brings no plugin type. It offers services, routes or tables to the capabilities that depend on it and is invisible to the catalog, modules and grants (`cap-acp`, the ACP session runtime).
- **Connection package**, `packages/plugin-<id>`: a service-only definition whose id is the id of the plugin type it brings (`plugin-repository`, `plugin-slack`, `plugin-claude-code`). It is the only kind of package that brings plugin types.

The daemon side lives under `src/` behind the package's root entry:

```
packages/cap-<id>/
  package.json        "exports": { ".": "./src/index.ts" }; dependencies name the platform packages and each capability dependsOn names
  drizzle.config.ts   schema ./src/schema/index.ts, out ./src/migrations
  src/
    index.ts          the root entry: the definition factory, service keys, ids, wire types, whatever dependents may use
    definition.ts     <id>Definition(options?) returning defineCapabilityDefinition({...})
    manifest.ts       defineCapability({...}); feature capabilities only
    wire.ts           Node-free request and response types; the package's own web layer imports it relatively
    package-root.ts   PACKAGE_ROOT and srcPath(...), resolved by package name
    schema/           one file per table group, each re-exported from schema/index.ts
    migrations/       generated by drizzle-kit and committed
```

The definition is built by a factory, `<id>Definition(options?)`, rather than exported as a value, so a distribution's tests can hand it fakes through options (`capabilityDefinitions(options)` in `apps/daemon/src/definitions.ts` is keyed by capability id for that reason). `package-root.ts` resolves the package by name (`createRequire(import.meta.url).resolve('@candy-mountain/cap-<id>')`) rather than from `import.meta.url`, because a distribution's bundle inlines the package's code but never its migrations folder, and `import.meta.url` would point into the bundle (`packages/cap-uptime/src/package-root.ts`).

## Registration

The platform discovers nothing. `startPlatform(dataDir, { product })` runs exactly what the `Product` it is handed lists (`src/product.ts`: the configuration from the SDK plus `capabilities`, `modules` and `pluginTypes`), and `assertProduct` refuses boot with `ProductError` when the configuration's ids and the supplied definitions disagree. Ahead of the product's list the platform puts its own definitions, `platformDefinitions()` (`src/platform-capabilities.ts`; today the service-only `threads` definition, which provides the session store `THREAD_SESSIONS`), so a product definition may name them in `dependsOn`. The platform also exports definitions a product chooses to list, `overviewDefinition` (the workspace home) and `platformAgentDefinition`; they are platform code but product choices, so they are in the product's list rather than injected.

A missing entry in an explicit list is a one-line diff to find; a scan that skipped a package is not. That is why a distribution imports each definition factory by name.

## The runtime definition

A capability's daemon half is one `CapabilityDefinition` (`@candy-mountain/platform-sdk/daemon`), passed through `defineCapabilityDefinition`, which runs `assertCapabilityDefinition` when the module is imported and throws `CapabilityDefinitionError` naming the capability. Every field but `id` is optional; a manifest-only definition such as the overview's starts to nothing. The daemon validates the whole list again at boot, before anything touches disk, so a bad definition stops the daemon with a message naming it and leaves no trace in the data directory.

```ts
// packages/plugin-repository/src/definition.ts
export const REPOSITORY_PATHS = serviceKey<RepositoryPaths>('repository.paths')

export function repositoryDefinition(): CapabilityDefinition {
  return defineCapabilityDefinition({
    id: REPOSITORY_CAPABILITY_ID,
    schema: { schema: repositorySchema, migrationsFolder: srcPath('migrations') },
    provides: [REPOSITORY_PATHS],
    pluginTypes: [repositoryPluginType],
    workspaceFacts: REPOSITORY_WORKSPACE_FACTS,
    start({ db }) {
      return {
        services: [bindService(REPOSITORY_PATHS, repositoryPaths(db))],
        workspaceRoutes: [repositoryRoutes()],
      }
    },
  })
}
```

### Ids

`id` is the capability id: a string matching `MANIFEST_ID_PATTERN` (lowercase letters and digits joined by `-`, `_` or `.`), equal to `manifest.id` when there is a manifest and to the `<id>` in the package name (`capabilityDependencyDrift`, below, checks the last). Plugin type ids, session family ids, service key names, activity event types and notification kinds follow the same pattern; workspace fact ids are camelCase (`FACT_ID_PATTERN`).

None of these is a closed list anywhere. Each is an open string, validated and registered when `startPlatform` builds its registries: it must match its pattern, be unique among what the list registers, and exist wherever it is referenced (a module member, a required plugin type, an agent's family, a required fact, an appended event type). A closed union in the SDK would mean adding a capability edits the platform, which a capability in another repository cannot do; validating at boot keeps a typo fatal, which is what the unions gave. `src/boot-ids.test.ts` proves the refusals.

### The manifest

`manifest` is the capability's declaration of what an actor can see and do: views, tools and operations, agents, jobs, the rung ladder (`none` first, each rung granting at least what the rung below grants), an optional `everyoneRung`, and its requirements (`requiresPlugins`, `requiresAnyPlugins`, `requiresWorkspaceFacts`, `requiresPlatformFacts`). It is written with `defineCapability` (SDK `./daemon` entry), which checks it on import; its types (`CapabilityManifest`, `Rung`, `ViewManifest`, `ToolManifest`, `NONE_RUNG`) are on the SDK's root entry. At boot the registry checks every manifest again, plus that capability, agent, tool, job and view ids and view paths are unique across manifests, and refuses with `CapabilityManifestError` naming the capability and the problem.

The manifest is separate from the runtime because different parts of the platform need them at different times. The manifest is plain data: the capability registry, modules, grants, the catalog, readiness and the registry answer are all computed from it, before any definition starts and without running capability code, and the catalog and registry answers the web reads are built from it. The runtime is code that opens timers, sockets and processes. Keeping the declaration as data means a bad manifest is refused before boot touches disk, and a capability's views and rungs can be reasoned about (granted, listed, gated) without starting it. A definition with no manifest is **service-only**: it is in no catalog, module or grant, and `capabilities.list()` leaves it out.

### Connection packages and plugin types

`pluginTypes` lists the plugin types the definition brings (`definePluginType({...})`). Only a definition with no manifest may bring one, and a `plugin-<id>` package's definition must bring the type named by its id; `assertCapabilityDefinition` refuses a manifest beside plugin types at boot, and `capabilityKindProblems` (in the boundary lint's module, run by the distribution's tests) refuses a `cap-` package that brings one or a `plugin-` package that has a manifest or lacks its type. The reason is collisions: two independently written features that both need Codex would each bring a `codex` type and the second would refuse boot (`Plugin type '<id>' is brought by both capability ...`). When the type belongs to a connection package that owns nothing to grant, both features require the type in their manifest (`requiresPlugins`) and share the one package. A connection has no views or rungs of its own, so it has no manifest. A feature that uses a connection's services, family or code declares the connection package in `dependsOn` like any other dependency (`cap-chat-codex` depends on `plugin-codex`).

A manifest's required plugin types must be brought by a definition in the list or supplied by the product (`Product.pluginTypes`), else boot is refused naming both; a type brought twice, or brought and also supplied by the product, is refused too.

### The other declarations

These are all read before boot touches disk, which is why they are declarations on the definition and not things `start` registers.

- `dependsOn`: capability ids this definition needs started first. See [Dependency declaration](#dependency-declaration).
- `sessionFamilies`: agent session families (`{ id, name }`) the definition runs. Registered before boot touches disk, so a manifest agent may name a family; an agent whose family nobody registers is refused (`SessionFamilyError`). The sessions themselves run through a service.
- `provides`: the service keys `start` binds, made with `serviceKey<T>(name)`. See [Services](#services).
- `schema`: the definition's migration set. See [Schema ownership](#schema-ownership).
- `activityEventTypes`: each event type the capability appends (`{ id, label, icon?, notifications? }`), with the notification kinds it raises. `appendActivityEvent` refuses an unregistered type (`ActivityEventTypeError`), so declaring the type is what lets the capability write the event; the web's activity filters and the notification rules page read the registered list.
- `workspaceFacts`: facts about a workspace the capability can answer from its own tables (`{ id, compute(db, workspace), message(label) }`). A manifest may require a fact any definition declares; one that no definition declares refuses boot naming both (`WorkspaceFactError`). `compute` runs on every registry read and gate check, so it must be a row lookup, never the network. `message` takes the product's scope label so the readiness reason says project, or whatever the product calls a workspace.

### start and the context

`start(context)` is synchronous and returns a `CapabilityRuntime`. Work that must wait (a store to initialise, a client to connect) is started inside `start` and awaited by whatever first needs it or by `close`, so one slow capability never holds the boot walk; the platform agent creates Mastra in `start` and waits for it on the first turn.

The `CapabilityContext` holds `db`, `paths` (`DataPaths`), `secrets` (the full store, with `get`), the `capabilities`, `modules`, `pluginTypes` and `families` registries, `workspaceFacts`, `agentMcp` (only `serversFor`), the product's `scopeUrlPrefix`, `scopeListPath` and `scopeLabel`, and `service(key)`. Read a variable the capability owns (`CM_UPTIME_*` in `cap-uptime`) inside `start`, with the factory's options overriding it: an invalid value then fails boot, and a product that does not list the capability never reads it. Daemon text a person reads names the workspace with `scopeLabel`, and links into the web app are built with `scopeUrlPrefix`.

### The runtime

Every field is optional:

- `services`: `bindService(key, value)` for exactly the keys in `provides`.
- `workspaceRoutes`: Hono apps mounted under the workspace prefix. See [Routes](#routes).
- `platformRoutes`: `{ path, routes }` mounted at an absolute path.
- `mcpServers`: MCP servers offered to agent sessions through the platform's agent MCP host; a server name two definitions offer refuses boot.
- `chatFamilies`: runners for families the daemon prompts in-process (`NativeFamilyRunner`); the family must be a registered session family and only one definition may run it.
- `notificationChannels`: ways the notification dispatcher can deliver; channel ids are unique, and the dispatcher tries channels in list order (`deliver` answering false means "no identity here, try the next").
- `workspaceAgents`: agents the capability adds per workspace (`WorkspaceAgentSource`), listed by the registry and run by the thread service.
- `onWorkspaceDeleted(workspace, deletion)`: see [Workspace deletion](#workspace-deletion).
- `close()`: see [Close](#close).

## Service lifecycle

### Boot

`startPlatform` works in this order, and each step finishes before the next begins:

1. Validate everything that is data: the product, the plugin types, the capability list (`createCapabilityRegistry`: each definition again, duplicate ids, the dependency graph, plugin types, session families, service keys), modules, session families of agents, activity event types, workspace facts, and the migration sets (`assertMigrationSets`). Nothing has touched disk yet.
2. Create the data directory, open the database and apply the migration sets.
3. Register the event types, seed the admin and its grants, open the secrets store.
4. Start the definitions (`startCapabilities` in `src/capabilities/start.ts`): the platform's own first, then the product's, **dependencies before dependents and list order otherwise**.
5. Start the agent MCP host over the definitions' MCP servers and the notification dispatcher over their channels.

If a `start` throws, or the claims in step 4 conflict (an MCP server name, a channel id or a chat family claimed twice), the definitions already started are closed in reverse and the error propagates, so a refused boot leaves no timer running.

### Services

A definition offers a service by naming its key in `provides` and binding it in `services`. The two must agree exactly: binding a key not provided, binding one twice, or providing one and not binding it refuses boot (`boundServices`). A key is provided by one definition in the list; a second provider refuses boot naming both. Export the key from the package's root entry, so a dependent imports it from there.

`context.service(KEY)` is the **service resolver**. It answers only keys bound by the definition's direct `dependsOn` entries, not their dependencies (`dependencyServices`), and throws for anything else. A capability that reads a service must therefore say so in `dependsOn`, and that one list is then the whole truth about what it needs: the start order, the boot refusal when a dependency is missing, and what its package.json must list all follow from it. Reaching a transitive dependency's service means declaring that dependency too (`bots` reads `REPOSITORY_PATHS`, so it lists `repository` itself even though `acp`, which it also lists, depends on `repository`).

Platform code never imports a capability, so when the platform needs a capability's service it reads a platform-owned key from the started list (`platform.runtime.service(KEY)`). `THREAD_SESSIONS` (`threads.sessions`) is the one that exists: the app serves chat threads only when something binds it. Services are values the definition built in `start`; they live until `close`.

### Routes

Every request, platform or capability, passes the auth middleware first, so a handler can read `c.var.actor`; only `/health`, `/auth/strategy` and a strategy's own public paths skip it. Type a route module with `new Hono<AppEnv>()`; `c.var` then carries `db`, `paths`, the registries, `workspaceFacts`, `workspaceAgents`, `secrets` (the write-only `SecretsWriter`: route handlers never receive a store that can read a secret back, and no route returns one), the scope fields and `actor`.

- **Workspace routes** (`workspaceRoutes`) are mounted under `WORKSPACES_PATH` (`/workspaces`), so a handler declares `/:slug/...` and the web reaches it as `/api/workspaces/<slug>/...` through the shell's proxy. Anything about one workspace goes here. The prefix gives the handler the slug param that the platform's gate reads: `requireCapability({ capability, view | tool | chat })` resolves the workspace from `:slug` (another param name through `slugParam`), answers 404 naming the workspace with the product's scope label when it does not exist, and otherwise refuses with the gate's code and status (`not_enabled` and `capability_unknown` 404, `not_granted` 403, `not_ready` 409) unless the actor's rung shows that view, tool or chat and the capability is ready in that workspace. The prefix does not gate anything by itself: every workspace route a capability mounts puts `requireCapability` (or `gateView`, `gateTool`, `gateChat` called in the handler) in front of its handler. Read the workspace with `getWorkspaceBySlug(c.var.db, slug, c.var.scopeLabel)`.
- **Platform routes** (`platformRoutes`) are mounted at their absolute `path` and belong to no workspace (`cap-uptime`'s `/monitor-sources` lists the monitor source types). The platform does not check them for collisions, so choose a path no platform route uses. Gate admin-only ones with `requireAdmin()`.

### Workspace deletion

Deleting a workspace runs every started definition's `onWorkspaceDeleted(workspace, deletion)`, dependents first, then deletes the workspace's plugin instances and the workspace row, all inside one SQLite transaction. A hook that throws rolls every row back and the workspace stays. Rows that reference `workspaces` with `onDelete: 'cascade'` need no hook; a hook is for what does not cascade (rows keyed by something else, secrets, files).

State a rollback cannot restore, such as files and secrets, must not be removed inside the transaction, or a later failure would leave rows pointing at files that are gone. Hand that work to `deletion.afterCommit(task)`: it runs only after the deletion has committed, and a failing task is logged rather than failing the delete. Read anything the cleanup needs before the rows go: `bots` reads the workspace's checkout from `repository` in its hook, then schedules the worktree removal with `afterCommit`.

### Close

`close()` is called in reverse start order, so a capability closes before anything it depends on. Every runtime is closed even when one throws, and the first error is rethrown. Closing the started list again returns the first run, so a definition's `close` runs once. The database is shut after every definition has closed, because a definition may still write while it closes (a session's last rows); the dispatcher and the MCP host stop before the definitions. Stop timers, watchers and child processes here; a capability that leaves one running keeps the process alive after shutdown.

## Schema ownership

### One set per package

Each package owns at most one migration set, declared as `schema: { schema, migrationsFolder }` (`CapabilitySchema`): `schema` is the package's Drizzle schema module (`import * as schema from './schema'`) and `migrationsFolder` the absolute path of its drizzle-kit output (`srcPath('migrations')`). Its set id is the capability id. At boot `migrationSets(definitions)` orders the sets: the platform's set (`PLATFORM_MIGRATION_SET`, id `platform`) first, then each definition's set in the same dependency order as start, so a set's foreign keys always point at tables that already exist. Each set is applied by Drizzle's migrator under its own migrations table, `migrationsTableFor(id)`: `__drizzle_migrations_<id>` with `-` and `.` folded to `_`. Separate tables mean one package's history never renumbers another's, so packages add migrations independently and a product without a capability gets none of its tables. `assertMigrationSets` refuses a repeated set id, two ids that fold to one table, or a folder without `meta/_journal.json` (`MigrationSetError`).

Migrations travel with the package because a capability that needed someone else's migration to run would not be a unit you can add, copy or remove.

### Generating migrations

The package's `drizzle.config.ts` points `schema` at `./src/schema/index.ts` and `out` at `./src/migrations`; `db:generate` and `db:check` scripts run drizzle-kit there (`pnpm --filter @candy-mountain/cap-<id> db:generate --name <short_name>`). Generated SQL, snapshot and journal entry are committed with the schema change, and the next daemon start applies them. Never edit an applied migration. Within one set Drizzle applies a migration only when its journal timestamp is newer than the last applied one, so after merging two branches that both added to a set, regenerate the later one.

Review generated SQL for a table rebuild (`__new_<table>`, `DROP TABLE`). The migrator runs each set in a transaction, where `PRAGMA foreign_keys=OFF` has no effect, so dropping a table that others reference with `ON DELETE cascade` deletes their rows. Rebuild only leaf tables; for a parent table, hand-write native `ALTER TABLE` statements and keep drizzle-kit's snapshot and journal entry (the platform set's `0001_agent_session_cwd_nullable` does this).

A distribution's test checks every set it boots against the latest snapshot in its folder and fails on schema changes with no generated migration (`apps/daemon/src/schema.test.ts`).

### What a capability may reference

- **Platform tables**, through the root entry: `workspaces`, `organisations`, `users`, `roles`, `userRoles`, `userPasswords`, `authSessions`, `roleGrants`, `workspaceModules`, `pluginInstances`, `platformMeta`, `activityEvents`, `chatThreads`, `chatThreadSessions`, `agentSessions`, `agentSessionEvents`. A capability's table names a workspace with a foreign key to `workspaces.id`, usually `onDelete: 'cascade'`, so the platform's delete removes its rows without a hook (`packages/cap-uptime/src/schema/`). Foreign keys to `chatThreads` and `agentSessions` exist too.
- **Its own tables.**
- **A dependency's tables**, only when `dependsOn` names that capability, since otherwise the table may not exist and the set order does not guarantee it is created first. The distribution's schema test fails when a set references any other table. Code that reads a table of a capability it does not depend on guards on `capabilities.has(id)`.

Queries name their table objects; `Db` is typed over no schema, so neither the platform's nor a capability's tables need a place in a shared type.

### What a capability never touches

- The platform's schema and migrations. A capability never adds a column to a platform table or a migration to the platform set; data it keeps about a platform row goes in its own table keyed by that row (the repository record is `repositories`, keyed by `workspace_id`, not a column on `workspaces`).
- Another capability's tables, outside a declared dependency, and never their migrations.
- Platform rows written behind the platform's back. Read platform tables directly when a lookup needs it (`cap-acp` reads `agentSessionEvents`), but write through the platform's functions: `appendActivityEvent` for activity (it checks the type and the payload size), the secrets store for secrets, `createPluginInstance` and its siblings for plugin instances, the workspace functions for workspaces. `platformMeta` is the one shared key-value table a capability writes directly, under a key prefix it owns (`cap-bots` keeps `slack-decision:` and `slack-handoff:` keys there and deletes them itself, since nothing cascades to them).
- The `__drizzle_migrations_*` tables, and the `mastra_*` tables Mastra creates in the same file.

## Dependency declaration

A capability depends on another when it reads its services, references its tables or imports its root entry. A manifest's required plugin types and workspace facts are not dependencies: boot checks them against the whole list (`cap-deployments` requires the `repository` plugin type without depending on `repository`, and `team` requires the `hasBots` fact that `bots`, which depends on `team`, declares). Every dependency is declared twice, and the two must agree:

- `dependsOn` in the definition, the runtime truth: start order, service resolution and table order follow it.
- `dependencies` in the package's `package.json`, the build truth: pnpm, Turborepo and the lint follow it.

`capabilityDependencyDrift` (exported from `@candy-mountain/platform-config/package-boundaries`) reports a capability package listed in `dependencies` that `dependsOn` omits, and the reverse, plus a definition whose id is not the package's `<id>`; a distribution runs it over every capability package in its tests (`apps/daemon/src/capability-packages.test.ts`, under `pnpm test`).

### Crossing a root entry

A capability reaches another capability only through that package's root entry (`@candy-mountain/cap-<id>` or `@candy-mountain/plugin-<id>`), never a subpath and never a relative path into it. Whatever the dependency exports from its root is its surface for dependents (service keys, ids, wire types, helpers such as `REPOSITORY_PATHS`); everything else in it is internal and may change without the dependent noticing. It reaches a platform package only through that package's declared `exports`: `@candy-mountain/platform-daemon` (its root entry; tests use the test entry point instead), `@candy-mountain/platform-sdk` and `@candy-mountain/platform-sdk/daemon`, and `@candy-mountain/platform-config`'s presets from config files (`*.config.*`) only. A package's own web layer may import its own `src/wire.ts` relatively. Wire types that more than one capability shares across the platform line belong in `@candy-mountain/platform-sdk`.

Allowed: capability -> platform (declared entries), capability -> a declared dependency's root entry, distribution -> platform and capabilities.

Forbidden: platform -> capability, capability -> a capability it does not declare, capability -> distribution, any relative path across package roots.

The platform side holds its half too: `src/seam.test.ts` fails when any file under this package's `src/` imports outside the package by a relative path, or imports a package other than the SDK, its own root, `@candy-mountain/platform-config` and the runtime libraries the daemon runs on, and when a folder appears under `src/` that it has not classified as platform.

### Refused at boot

`startPlatform` refuses to start, naming the capability, when a definition:

- depends on itself, repeats a dependency, or names one with an invalid id (`CapabilityDefinitionError`, from `assertCapabilityDefinition`);
- depends on a capability that is not in the definition list, or the dependencies form a cycle (named in order);
- asks `context.service` in `start` for a key no direct dependency binds;
- requires a plugin type nobody brings or supplies, or a workspace fact nobody declares;
- has a manifest and brings plugin types;
- names an agent family nobody registers.

### Refused at lint

The `cm-packages` lint (`packages/platform-config/eslint/package-boundaries.mjs`) runs on every script file of every package through the platform-config ESLint preset (`packageBoundaries()`), under `pnpm lint`. Its messages end with the allowed directions (`DIRECTIONS`) and its rule docs point here.

- `cm-packages/no-relative-cross-package`: a relative import whose path leaves the importing package's root.
- `cm-packages/no-subpath-import`: a workspace package imported through an entry its `exports` does not declare, a capability package imported through anything but its root entry (from another package), or a platform-config preset entry imported outside a config file.
- `cm-packages/no-undeclared-capability-import`: a capability package importing a capability package its `package.json` `dependencies` do not list, so its definition cannot name it in `dependsOn` either.
- `cm-packages/no-capability-import-from-platform`: a platform package importing a capability package.
- `cm-packages/no-unlisted-dependency`: any import of a workspace package that the importing package's `dependencies` or `devDependencies` do not list, so Turborepo would not invalidate the importer when it changes.
- `cm-packages/no-distribution-import`: a capability or platform package importing a distribution (an app under `apps/`), its test helpers included. A capability's tests take what they need from the test entry point (see Testing).

The package kinds come from names alone (`kindOf`: `@candy-mountain/platform-*` is platform, `cap-*` and `plugin-*` are capabilities, anything else is other), discovered from the pnpm workspace's `package.json` files (`workspacePackages`); two capability packages carrying one id fail lint. The `plugin-`/`cap-` rule is checked against the definitions themselves, which a lint cannot load, by `capabilityKindProblems` in the distribution's capability-package test. `packages/platform-config/test/unit/package-boundaries.test.ts` lints the fixture workspace in `test/fixtures/workspace/` and asserts each rule fires.

Fix a finding by declaring the dependency in both places, importing through the root entry, or moving the shared type into the SDK; do not disable the rule.

## What the platform keeps stable

Nothing is versioned yet: every package is private and consumed with `workspace:*`. The platform-package plan (`.ai-docs/plans/platform-package/`) publishes the platform packages on one version line where a breaking change to the contract below is a major. Until then this list is what capability code may rely on and what platform changes must treat as the contract.

The contract:

- Everything on `@candy-mountain/platform-sdk/daemon`: the definition, context and runtime types, the define helpers (`defineCapabilityDefinition`, `defineCapability`, `definePluginType`, `serviceKey`, `bindService`), the declaration types, `AppEnv`, `Db`, `DataPaths`, the registry interfaces and the error classes.
- The wire types, id patterns and manifest types on `@candy-mountain/platform-sdk`'s root entry.
- What `@candy-mountain/platform-daemon`'s root entry exports for capability code: the route helpers and gates (`requireCapability`, `gateView`, `gateTool`, `gateChat`, `requireAdmin`, `resolveActorRungs`), actor and workspace lookups, plugin instance and plugin secret functions, activity, notification helpers, the thread and session exports including `THREAD_SESSIONS`, the agent MCP types, and the platform tables as foreign-key targets and read sources.
- The behaviour this document describes: ids validated at boot, dependencies started first and closed last, `context.service` limited to direct dependencies, workspace routes under `/workspaces`, the deletion transaction with `afterCommit`, one migration set per package under its own migrations table, applied after the platform's and its dependencies' sets.

Internal, and free to change:

- Anything not on a declared entry: every file under `src/`, which the lint already keeps out of reach.
- What the root entry exports for distributions rather than capabilities: `startPlatform`, `createApp`, `runDaemon`, `loadDaemonConfig`, the registry constructors, `startCapabilities`, `migrationSets` and the product checks. A capability never starts a platform or builds an app.
- The platform set's migration history and the columns of platform tables beyond the keys a capability references.
- The wording of error and log messages (that a refusal names the capability is kept; the sentence is not).

Test support is not part of this production contract. A capability's tests reach the platform through the dedicated test entry point, described below.

## Testing

A capability's tests import test support from `@candy-mountain/platform-daemon/testing` only, never from a distribution: not `apps/daemon/src/testing`, which wraps the same kit with Candy Mountain's product for the distribution's own tests. The kit there starts a platform over the capability under test and the platform packages alone, and gives an actor at a chosen rung, a workspace with chosen facts, a plugin instance with fake secrets and a restart over the same data directory. [`TESTING.md`](./TESTING.md) documents it. `cm-packages/no-distribution-import` refuses an import of a distribution, and the production root entry exports no test support, so a test reaching for either fails lint or typecheck.
